> 「为什么不走 C++ 移植」的依据。

## 结论

**推荐方案 C：把现有 C/C++ 去 Qt 化后当静态库链进来，而不是用 Swift 重写。**
但**不建议现在做** —— 它应排在「当前 Swift 版在真机上跑通并验过一轮」之后，
且需要先确认一件产品层面的事（见文末「需要你拍板的一件事」）。

## 事实核查（不是印象，是查过的）

我一开始以为「macOS 上网关本来就是 stub」，**这个假设是错的**，查 `CMakeLists.txt` 才发现：

```cmake
if(CMAKE_SYSTEM_NAME STREQUAL "Linux" OR APPLE OR WIN32)
    # …编入真实现：NetStack + lwIP + LanGateway_linux.cpp（实为 POSIX 通用）
```

`APPLE` 在**真实现**那一支里，二层走 `L2Endpoint_mac.cpp`（BPF）。
所以这是 Qt 版 macOS 上**真实存在的功能**，移植它属于「恢复对等」，不是「新增功能」。

| 项目 | 数字 |
|---|---|
| `src/net/**` 总量 | 9,001 行 C++ |
| 其中与 macOS 无关（Win/Linux 的二层端点 + stub） | ≈ 1,900 行 |
| **macOS 实际需要的** | **≈ 7,100 行 C++** |
| vendored lwIP（`third_party/lwip`） | 135,473 行**纯 C，零 Qt** |
| 带 `Q_OBJECT` 的头文件 | 11 个里有 7 个 |
| Qt 符号出现次数（QObject/QString/emit…） | ≈ 1,000 处 |

两条关键的**有利**事实：

1. **lwIP 是纯 C、零 Qt**，无论走哪条路都是原样复用 —— 没有人会用 Swift 重写一个 TCP/IP 栈。
2. **macOS 上已有 headless 自检**：`GatewaySelfTest.cpp` 在 mac 用 `feth` 接口 + **真实 BPF 端点**
   跑通整条链路（`COAST_GATEWAY_SELFTEST`）。这条极其重要 —— 它意味着一次去 Qt 化重构
   **是可验证的**，而不是「改完只能祈祷」。这也是我敢推荐方案 C 的主要原因。

一条关键的**不利**事实：

3. Qt 耦合**很深且很散**：7/11 个头文件是 `QObject` 子类，靠信号槽串联；`QString`/`QByteArray`
   贯穿始终。不是「换几个类型」就完事的。

## 四个选项

| | 方案 | 评价 |
|---|---|---|
| A | 用 Swift 重写这 7,100 行 | **否决**。包级别的收发、状态机、超时重传，已经调通且有自测；用 Swift 重写一遍买不到任何东西，只买风险。而且 lwIP 那 13 万行照样得用 C。 |
| B | 原样把 C++ 链进来 | **否决**。它依赖 QObject/信号槽/QString，等于把 Qt 拖回 Swift 版 —— 那这次重构的意义就没了。 |
| C | **去 Qt 化后作为 SPM 的 C/C++ target 链进来** | **推荐**。工作量集中在机械替换（`QObject`+信号 → 回调接口；`QString` → `std::string`；`QTimer` → 自己的调度），且**有自测兜底**。lwIP 完全不动。 |
| D | macOS 版不做这个功能 | 可接受的降级，但要**明说**，不能留个点了没反应的开关。 |

### 为什么没有「用 macOS 原生方案」这一项

有人会想到 NetworkExtension。**它解决不了这个问题**：
`NEPacketTunnelProvider` / `NETransparentProxyProvider` 接管的是**本机**的流量。
而这个功能的本质是**把局域网里别的设备的流量骗到本机来**（ARP/NDP 投毒），
那是二层的事，NetworkExtension 完全不涉及。所以只有「复用现有实现」或「不做」两条路。

## 方案 C 的落地步骤（若决定做）

1. **先把 lwIP 单独立成 SPM 的 C target**，跑通 `swift build`。这一步零风险，纯配置。
2. **给 `src/net/**` 剥 Qt**，在 C++ 侧收敛成一个不含 Qt 的门面（`extern "C"` 或
   C++ interop 的少数几个类）。**每剥一个文件就跑一次 `COAST_GATEWAY_SELFTEST`**，
   而不是全部改完再跑 —— 这套代码的错误多数不会当场崩，只会表现成「偶发丢包」。
3. **Swift helper 补一个 `openBpfForInterface`**：`/dev/bpf*` 需要 root，
   C++ 版的 helper 协议里已经有这个方法（开好、配好 BIOCSETIF/PROMISC 后把 fd 经
   XPC 传回应用），Swift 版照抄一个即可 —— 这一步很小。
4. **然后**才做 `DeviceStore` / `LanScanner` / `DevicesPage`（PLAN 阶段 6 里那三项 `[~]`）。

顺序不能反：先做设备页会得到一个「开关点了没反应、流量恒为 0」的假页面。

## 风险

- 步骤 2 是在**正在工作的、时序敏感的**代码上做手术。自测能覆盖主链路，但覆盖不到
  「真实局域网里各种奇怪设备」的长尾。
- 去 Qt 化会**同时影响 Qt 版**（如果两边共用这份代码的话）。若不想动 Qt 版，就得
  接受一份分叉的副本 —— 那又带来长期的双份维护。**这一点建议在动手前明确。**

## 需要你拍板的一件事

**macOS 上「代理局域网里其它设备」这个功能，到底要不要？**

- 要 → 按上面四步做，我估计主要成本在步骤 2，且必须配合真机（真实局域网 + 真设备）验证，
  不是 CI 能覆盖的。
- 不要 → 我把 PLAN 里那三项 `[~]` 改成明确的「macOS 版不提供」，
  并在设备页位置放一句说明（而不是留个空页或死开关）。

在你拍板之前，我**不会**去动 `src/net/**` —— 这是唯一一处「做了可能白做」的地方。

## 一个不依赖这个决定、现在就能做的东西

即使不做网关，**局域网设备发现本身是可以单独成立的**：读 ARP/邻居表就能列出
「这个网络里有哪些设备」，不需要 lwIP、不需要投毒、不需要 root。
它是一个**完整的小功能**（看得到、有用），而不是大功能的半成品 ——
前提是**不显示那个点了没用的「代理」开关**。

如果你觉得有价值，我可以先做这个只读版设备页。

# 最终方案（2026-07-31 拍板）

**零配置透明代理：用户只在软件里点开关，设备端什么都不用改。零行 C++、不引 lwIP。**

> 中途我出过一次偏差：先设计成「让用户在设备上手动填代理地址」。
> 那等于没做这个功能 —— **零配置正是它的全部意义**。已纠正，记在这里以免重蹈。

## 链路

1. **ARP 欺骗** —— 让目标设备把本机当成网关，它的流量于是发到我们网卡上；
2. **`net.inet.ip.forwarding=1`** —— 让内核愿意转发这些不是发给自己的包；
3. **PF 的 `rdr` 规则** —— 把该设备的 TCP 重定向到 mihomo 的 `redir-port`(7893)、
   UDP :53 重定向到 mihomo 的 DNS 口(1053)；
4. mihomo 按规则分流。

## 关键：为什么这条路不需要 lwIP

Qt 版背那 13 万行用户态 TCP/IP 栈，是因为它在**二层**自己收发帧、自己重组 TCP ——
包到了网卡就得自己从以太网帧一路解到 TCP 流。

而 macOS 上 **内核转发 + PF 重定向** 把这一整层全省了：包由内核按正常网络栈处理，
PF 只是在路由前把目的地址改到本机的 redir 口。我们只负责两件事：**让流量来**（ARP 欺骗）、
**让它拐弯**（PF 规则）。这就是同一个问题的 macOS 原生答案。

| | Qt 版 | Swift 版（macOS 原生） |
|---|---|---|
| 让流量过来 | ARP/NDP 投毒 | **ARP 欺骗（同样）** |
| 收包与协议栈 | 自己开 BPF + lwIP 13 万行 | **内核转发**，零代码 |
| 交给核心 | 自己拨 SOCKS | **PF rdr → redir-port** |
| 需移植的 C++ | ≈ 7,100 行 | **0 行** |
| 设备端成本 | 零配置 | **零配置（同样）** |

## 身份口径的差异

透明重定向下**看不到任何凭据**，设备只能按**源 IP** 识别，所以每设备策略是
`SRC-IP-CIDR,<ip>/32,<目标>`（Qt 版走 `IN-USER`，那是它经带认证 SOCKS 拨号的产物）。

台账主键仍是 **MAC** —— IP 会随 DHCP 漂移，MAC 才是稳定身份。每轮扫描把当前 IP
刷进台账，变了就重新生成规则。`lastIP` 落库而不是只放内存：设备暂时不在邻居表里
（睡眠、刚重启）时规则不能凭空消失 —— 那会让它在恢复的一瞬间直连出去。

## 需要 root 的部分（走特权 helper）

- 写 ARP 应答（`/dev/bpf*`）
- `sysctl net.inet.ip.forwarding=1`
- 装/卸 PF anchor 规则

主混合端口（`mixed-port`）不受影响：仍 `allow-lan: false` 只监听本机。
`redir-port` 也**不对外广播** —— 它只接受经内核重定向进来的连接，开着它不等于开放代理。

## 顺带验证过的一件事

在改方向之前，我已经把 lwIP 立成 SPM 的 C target 并**成功编过全部 32 个源文件**
（符号链接到 `clashauto-c++/third_party/lwip`，源码一份不复制）。
结论是「C++ 移植这条路技术上走得通」—— 现在不走了，但如果将来真需要透明代理，
第 1 步是已知可行的，不必重新趟。
