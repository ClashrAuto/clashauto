# 找 lwIP 的替代品 —— 候选调研与逐轮实测记录

> 本文是**实测记录**，不是方案书。每轮测试都往「测试记录」一节追加，**只增不改**；
> 结论被后续数据推翻时，保留原记录并在下面写明推翻理由（本仓库里所有性能结论都这么记，
> 见 `src/net/NetStack.h` 顶部那一大段）。

## 1. 为什么要换

lwIP 现在承担的是「被劫持设备的以太帧 → 终结 TCP → 转投 mihomo」这条数据面
（`src/net/NetStack.cpp`，vendored `third_party/lwip`）。它有两个已经被实测钉死的问题：

**① 吞吐天花板是结构性的，不是常数因子。** 已测（树莓派网关，千兆链路，netns 假外网满速加压）：

| 数据面 | 吞吐 | 折算 |
|---|---|---|
| lwIP | 944 Mb/s @ 0.90 核 | **0.95 核/Gbps** |
| TPROXY（内核转发） | 940 Mb/s @ 0.24 核 | 0.25 核/Gbps |

lwIP 是 `NO_SYS` **单线程**（`lwip_init`/ARP 表/PCB 链全局），单核封顶 ≈ 1.05 Gbps。
加机器、换 CPU 都不解决——瓶颈是「所有流量串行过一个线程」这个结构。

**② 抗压性差。** 单台设备的 DNS 洪水 + 并发 TCP 能稳定打崩 lwIP 的 assert
（有稳定复现配方；`11fc9ac` 修的 `lwipAccept` 漏 `ERR_ABRT` 是其中一个根因，
但纯 DNS / 纯 TCP 都不崩，说明是混合负载下的状态机边界）。这条比吞吐更要命。

**③ 已经排除的一条路：** 「让核心自带的 TUN inbound 接手」——2026-08-04 实测
`stack: system` 与 `stack: gvisor` 在 Windows 真机上**区间完全重叠、CPU 折算相同**
（2743 vs 2666 Mb/s，都是 0.45 核/Gbps），换栈拿不到收益。所以本轮找的是
**替换 NetStack 内部那个用户态栈**，不是换核心的 TUN 实现。

## 2. 候选矩阵

Coast 的网关是 L2 ARP 投毒式的，Windows / macOS 上没有 TPROXY 这种内核转发可用，
所以**跨平台候选必须是用户态栈**；内核路线只能作为 Linux 上的上限参考。

| # | 候选 | 语言 | 并行模型 | 接入成本 | 备注 |
|---|---|---|---|---|---|
| A | **lwIP**（现状） | C | 单线程 NO_SYS | 0（已在用） | 基线 |
| B | **gVisor netstack** (`gvisor.dev/gvisor/pkg/tcpip`) | Go | 多 goroutine，天然跨核 | 高：得起独立进程或 c-shared | mihomo / sing-tun 在用，工程成熟度最高 |
| C | **smoltcp** | Rust | 单线程（可分片） | 中：FFI / cxx 桥 | 体积小、无 alloc，抗压性未知 |
| D | **libslirp** | C | 单线程 | 低：与 lwIP 同形（喂帧 + 自己 dial socket） | QEMU 用户态网络在用 |
| E | 内核栈（TUN + TPROXY / 路由） | — | 内核，跨核 | Linux-only | **仅作上限参考**，已知 0.25 核/Gbps |
| F | lwIP 分片（N 实例 / N 线程） | C | 手工分片 | 低 | 不是替换，是把 A 的结构性上限拆开 |
| — | F-Stack / mTCP / DPDK / VPP | — | — | 不可行 | 要独占网卡 + 大页，桌面客户端上直接出局 |

## 3. 测试方法

### 3.1 台子

`root@192.168.20.239`，Ubuntu 24.04，x86_64 **8 核 / 31 GB**，内核 6.8.0-136。
选它是因为**回环带宽远高于任何用户态栈的上限**（见下面 R1 的 42~46 Gbps），
量出来的一定是栈自己的天花板，而不是链路的。

harness 在 `/root/stackbench/`（源码同步在仓库 `clashauto-c++/bench/stackbench/`）。

### 3.2 拓扑（各栈统一）

```
iperf3 client ──> sb0 (TUN, 10.99.0.1/24, 路由 10.99.0.0/24)
                    └─> 被测栈：终结这条 TCP，再用内核 socket 连 127.0.0.1:5201
                                                    └─> iperf3 server
```

和生产里 `NetStack` 干的事同形（终结一条 TCP + 把字节搬到另一条 TCP），
只是把 SOCKS5 那一跳换成直连，免得把 mihomo 的开销混进来。

### 3.3 量三件事

- **吞吐**：`iperf3 -J`，取 `end.sum_received.bits_per_second`。
  ★ **单次不可信**——本仓库已经在这上面栽过两次（单轮采样得出「gvisor 快 27%」，
  复测 3 轮抹平）。所以每个栈**至少 3 轮取中位**，并把 3 个值全记下来。
- **CPU**：被测进程 `/proc/<pid>/stat` 的 `utime+stime` 差分（含所有线程）→ 核·秒，
  再折算 **核/Gbps**（唯一能跨吞吐档次比较的口径）。同时记整机忙碌核数做交叉校验。
- **延迟**：建连时间 + 小请求往返 p50/p99（乒乓包，不是 ping——要走栈里的 TCP 路径）。

### 3.4 对照组（关键）

光量「某个栈多少核/Gbps」没有分母。所以先测两条线：

- `ctl-loopback` —— iperf3 直打回环：**这台机器的天花板**。
- `ctl-relay` —— 一个**没有任何 IP 栈**的单线程 `epoll + splice` 中继（`relay.c`）：
  「只搬字节」的**地板成本**。任何栈都躲不掉这一份，超出的部分才是栈自己的协议开销。

### 3.5 清理协议（每轮测试前强制）

`clean.sh`，做完会**打印断言并在没清干净时退出非零**（不是「说清了」而是「证明清了」）：

1. 杀掉被测栈 + iperf3 + relay（先 TERM 后 KILL）；
2. 删掉本 harness 建的 `sb*` TUN 设备（**只删 `sb[0-9]+`**，绝不碰机器上已有的
   `vdev*` / `docker0` —— 那是别的测试留下的）；
3. 删掉 `10.99.0.0/24` / `203.0.113.0/24` 路由残留；
4. `sync` + `drop_caches=3`，等 1 秒让 TIME_WAIT 端口放掉；
5. 断言 `procs=0 tun=0 listen=0`，并打印当时的整机 idle%（起跑线不干净就别开量）。

### R1 · 2026-08-03 19:36 UTC · 对照组基线

清理断言：`procs=0 tun=0 listen=0 idle%=99.95`（起跑线干净）。`DUR=10`。

| 用例 | 栈 | 吞吐 | 重传 | 被测进程 CPU | 整机 CPU | 折算 |
|---|---|---|---|---|---|---|
| `ctl-loopback` | 无 | **41.99 Gbps** | 0 | — | 16.83 核·秒 | 0.040 核/Gbps（整机口径） |
| `ctl-relay` | 无（splice） | **46.32 Gbps** | 0 | **9.99 核·秒** | 28.76 核·秒 | **0.022 核/Gbps**（进程口径） |

读法：

- 台子本身能到 **42 Gbps**，比 lwIP 的 ~1 Gbps 上限高一个半数量级 → **台子不会是瓶颈**，
  后面量到的每一个天花板都是栈自己的。
- `ctl-relay` 进程 9.99 核·秒 / 10 s = **0.999 核**——它已经把单核跑满了，
  也就是说「单线程 + splice 零拷贝、完全不做 IP 栈」在这台机器上是 **46 Gbps/核**。
  这就是地板：**lwIP 的 0.95 核/Gbps 里，只有 0.022 是搬运，其余 97.7% 是协议处理开销。**
- relay 比直连回环还快 4 Gbps 并不矛盾：直连那轮 iperf3 客户端/服务端两头都在同一
  调度域里抢核，relay 那轮多了一跳但把收发拆到了更多核上（整机忙碌 28.8 vs 16.8 核·秒）。
  两个数各自只做各自的分母用，不互相比较。

（**没通过就不许开量**——本仓库栽过「只看日志 armed 就开量、其实接管没生效」的跟头）。

`DUR=10`，吞吐 3 轮，延迟 500 次串行乒乓。

| 轮 | 吞吐 | 重传 | 栈进程 CPU | 折算 |
|---|---|---|---|---|
| 1 | 1.119 Gbps | 0 | 9.99 核·秒 | 0.893 核/Gbps |
| 2 | 1.121 Gbps | 0 | 10.00 核·秒 | 0.892 核/Gbps |
| 3 | 1.110 Gbps | 0 | 10.01 核·秒 | 0.902 核/Gbps |
| **中位** | **1.119 Gbps** | 0 | **1.00 核（跑满）** | **0.893 核/Gbps** |

延迟（走栈的 TCP 小包往返，不是 ICMP）：

| 建连 | p50 | p90 | p99 | 最大 |
|---|---|---|---|---|
| 1.19 ms | **0.074 ms** | 0.082 ms | 0.092 ms | 0.178 ms |

读法：

- **单核封顶被独立复现了。** 三轮 CPU 全是 9.99~10.01 核·秒 / 10 s = **恰好 1.000 核**，
  也就是说 1.119 Gbps 不是链路给的、也不是靶机给的，是 lwIP 把一个核跑满后给出的上限。
  台子还剩 7 个核闲着（整机才 15.9 核·秒），它一个都用不上。
- **0.893 核/Gbps，与树莓派上量到的 0.95 核/Gbps 吻合。** 两台机器架构不同（ARM vs x86）、
  链路不同（千兆物理网卡 vs TAP+回环）、出站不同（经 SOCKS5 到 mihomo vs 直连），
  折算值只差 6% —— 这是一次**跨台子的交叉验证**，说明 0.9 核/Gbps 是 lwIP 自己的常数，
  不是某台机器的偶然。
- **延迟这一项 lwIP 没有问题**：p50 74 µs、p99 92 µs、最大 0.178 ms，尾部只有 p50 的 2.4 倍。
  建连 1.19 ms 里绝大部分是 python 侧开销。**换栈的动机不在延迟上**，别拿延迟当理由。
- 对比 R1 的地板（`ctl-relay` 0.022 核/Gbps）：**lwIP 每 Gbps 的开销是纯搬运的 41 倍。**

**方法学上踩到的两个坑（记下来免得再踩）：**

1. `tcp_bind(pcb, IP_ANY_TYPE, 0)` 里的 `0` 是「**自动分配一个端口**」，不是「通配」。
   catch-all 必须在 `tcp_listen_with_backlog()` **之后**再 `lp->local_port = 0`，
   否则 `tcp_in.c` 的通配分支永远命中不了，所有 SYN 被 RST。
   `NetStack.cpp` 里本来就有这一行，harness 漏抄了，症状是 `Connection refused` +
   tcpdump 看到 lwIP 立刻回 `R.`。
2. 经 ssh 起后台进程必须 `setsid … </dev/null >log 2>&1 &`，否则它攥着会话的 stdout，
   远程命令跑完也不返回（表现为「命令卡死 5 分钟」）。

**尚未测**：B（gVisor netstack）/ C（smoltcp）/ D（libslirp）/ E（内核栈）/ F（lwIP 分片）
一个都还没量。R2 只把候选 A 的基线钉死了。

### A vs B 摆一起

| | lwIP | gVisor | 谁赢 |
|---|---|---|---|
| 吞吐中位 | 1.119 Gbps | **2.570 Gbps** | gVisor **2.30×** |
| 用掉的核 | 1.00（封顶） | 2.84 | lwIP 少 |
| **核/Gbps** | **0.893** | 1.105 | **lwIP 省 19%** |
| 往返 p50 | **0.074 ms** | 0.131 ms | lwIP 快 1.8× |
| 往返 p99 | **0.092 ms** | 0.167 ms | lwIP 快 1.8× |
| 10 s 重传 | **0** | 15~70 | lwIP 干净 |

**这一轮最该记住的一句话：gVisor 不是更省，是更能并行。**

按每 Gbps 的 CPU 代价算，gVisor 比 lwIP **贵 24%**；延迟每一项都差 1.8 倍。它之所以快
2.3 倍，纯粹是因为它肯用 2.84 个核，而 lwIP（`NO_SYS=1` 单线程）到 1.00 核就再也上不去了。

于是换不换栈这件事，取决于痛点是哪一个：

- **痛点是「x86/多核机器上限太低」** → gVisor 有效，天花板直接抬 2.3 倍，而且 2.84/8 核
  说明它还没吃满机器（瓶颈很可能在单 TAP fd 的收包 goroutine 上，多队列还能再抬）。
- **痛点是「树莓派上 CPU 烧太多」** → gVisor **帮倒忙**。核少的机器上并行度换不出吞吐，
  只剩下每 Gbps 贵 24% 这个纯亏损。
- **痛点是延迟** → 两边都不该动，lwIP 本来就更好（见 R2）。

**一个必须挑明的配置不对等**：lwIP 是 `TCP_WND`/`TCP_SND_BUF` 固定 128 KiB（受 `MEM_SIZE`
约束），gVisor 是自动调窗（默认可涨到 MB 级）。gVisor 那 2.3 倍里有多少来自「窗口更大」
而不是「栈更好」，现在分不出来 —— 这正是候选 F（只把 lwIP 的窗口调大）存在的意义，
**在跑完 F 之前，不要把 2.3× 记成 gVisor 的架构优势**。

另：第 1 轮 2.158 Gbps / 70 次重传是明显的热身离群点（Go 运行时预热 + 窗口爬坡），
第 2、3 轮才稳定。三轮取中位这个做法又一次挣回了自己的成本。

**尚未测**：C（smoltcp）/ D（libslirp）/ E（内核栈）/ F（lwIP 加窗）。

### R4 · 2026-08-03 20:26 UTC · 候选 F = lwIP 加窗，兼 A/B 复测

R3 结尾留了个未拆的混淆因子：lwIP 窗口固定 128 KiB、gVisor 自动调窗可到 MB 级，
那 2.3× 里有多少是窗口的功劳？这一轮把它拆掉。

候选 F = **同一份 lwIP 源码、同一个 `lwip2socks.c`，只把 lwipopts 的窗口从 128 KiB 提到
1 MiB**（`TCP_WND` / `TCP_SND_BUF` 各 1 MiB，`TCP_RCV_SCALE` 2→5，`MEM_SIZE` 16→64 MiB）。
lwipopts 由生产那份 **sed 派生**，不是手抄。三个候选在同一次、验证过空闲的机器上背靠背重测。

| 栈 | 吞吐中位 | 用掉的核 | 核/Gbps | 往返 p50 | 往返 p99 | 重传 |
|---|---|---|---|---|---|---|
| lwIP 128 KiB | 1.132 Gbps | 1.00 | 0.883 | 0.078 ms | 0.121 ms | 0 |
| **lwIP 1 MiB** | **1.146 Gbps** | **1.00** | **0.873** | 0.067 ms | 0.081 ms | 0 |
| gVisor | 2.609 Gbps | 2.83 | 1.089 | 0.118 ms | 0.174 ms | 10~55 |

**结论：窗口放大 8 倍，吞吐纹丝不动（+1.2%，在轮间噪声里）。**

所以 R3 那个「先别把 2.3× 记成架构优势」的保留意见，现在可以撤销了：
**gVisor 的 2.3× 与窗口无关，就是并行度换来的。** lwIP 的瓶颈也随之定位得更死——
它不是「窗口不够大所以喂不满」，而是**单线程的每包处理成本**把一个核吃干了；
加窗只是让它更快地撞上同一堵墙（1.00 核，三轮一字不差）。

顺带一个小收获：加窗后延迟反而**更好**（p99 0.121 → 0.081 ms）。合理——窗口大了，
`tcp_recved` 触发的窗口更新 ACK 变少，每包的簿记开销下降。加窗不亏，只是不解决主要问题。

#### 这一轮真正的教训：清理门禁形同虚设，被抓了个正着

R4 第一次跑出来的数和上面这张表几乎一样，但**那次的机器是脏的**——上一轮的
`lwip2socks_big` 没被杀掉，TAP 被删后它的 epoll 循环空转，满满占着一个核。
两个洞叠在一起才让它活下来：

1. `pkill -x lwip2socks` 匹配不上 `lwip2socks_big`（`-x` 要求进程名完全相等）；
2. **门禁看的是 `/proc/stat` 的开机累计 idle%**——一个 100% 空转的进程只把这个数从
   99.9 压到 97.8，看着完全正常。**累计量根本不可能反映"此刻忙不忙"。**

改成 `pkill -f 'bin/(lwip2socks|…)'` 之后踩了更狠的一脚：调用方自己的命令行
（`./bench_stack.sh lwip-128k ./bin/lwip2socks`）也含这串，**clean.sh 把自己的父 shell
连同整条 ssh 会话一起杀了**，症状是「远程命令毫无输出直接返回」，极难往清理脚本上想。

最终修法：

- **按 `readlink /proc/<pid>/exe` 的真实可执行文件路径杀**，不按命令行。`./bin/x` 起的能
  匹配上，而 shell/sshd 的 exe 是 `/usr/bin/bash`，天然不会误伤自己。
- **门禁改采样 1 秒的瞬时 CPU 占用**，超过 0.30 核直接判失败，并打出 top 进程。
- `bench_stack.sh` 的 teardown 改成 **杀整个进程组**（`kill -- -$SPID`），不留孤儿。
- 门禁本身做了**证伪自测**：跑一个 `yes >/dev/null` 让它必须 FAIL（实测 `busy_cores=1.007
  → FAILED`），再在空闲时必须 PASS。**一个从来没失败过的断言不算断言。**

老实说：重测后的数与污染时的数几乎一致（8 核机器上多一个满载核并没挤到被测进程），
**结论没变**。但门禁本来就不该放它过去——这次侥幸，下次未必。

**尚未测**：C（smoltcp）/ D（libslirp）/ E（内核栈）。

### 四个候选横排（全部同机同 harness，机器均验证空闲）

| 栈 | 吞吐中位 | 用掉的核 | 核/Gbps | p50 | p99 | 重传 |
|---|---|---|---|---|---|---|
| lwIP 128 KiB | 1.132 Gbps | 1.00 | 0.883 | 0.078 ms | 0.121 ms | 0 |
| lwIP 1 MiB | 1.146 Gbps | 1.00 | 0.873 | 0.067 ms | 0.081 ms | 0 |
| gVisor | 2.609 Gbps | 2.83 | 1.089 | 0.118 ms | 0.174 ms | 10~55 |
| **smoltcp** | **4.636 Gbps** | **1.00** | **0.215** | 0.076 ms | 0.096 ms | 0 |

**smoltcp 在同样的一个核上跑出了 lwIP 的 4.1 倍吞吐，每 Gbps 便宜 4.1 倍；
比 gVisor 快 1.8 倍，而 gVisor 用的核是它的 2.8 倍。延迟与 lwIP 持平。**

### 4 倍这种数必须先证伪再相信 —— 用网卡自己的计数器对量级

同样 5 秒、同样的靶，读 `ip -s link show sb0`（内核侧的硬计数，不是被测程序自报）：

| | lwIP | smoltcp |
|---|---|---|
| iperf 吞吐 | 1.096 Gbps | 4.445 Gbps |
| sb0 tx（栈→内核）| 473,060 包 / **平均 1503 B** | 1,924,577 包 / **平均 1498 B** |
| sb0 rx（内核→栈）| 236,573 包 / 平均 54 B | 42,683 包 / 平均 54 B |
| CPU | 4.99 核·秒 | 4.99 核·秒 |
| **每包成本** | **7.03 µs** | **2.54 µs** |

两条硬事实：

1. **平均帧长 1503 vs 1498 B —— 没有任何 offload/巨帧作弊。** 两边都是老老实实一帧一帧
   在发 1500 字节，smoltcp 就是在同样的 CPU 预算里多处理了 2.8 倍的包。
2. 但**ACK 比例差得离谱**：lwIP 每发 2 个数据包收 1 个 ACK，smoltcp 每发 **45** 个才收 1 个。
   这说明 smoltcp 的发送是成批灌进 TAP 的，触发了接收侧内核的 GRO 合并，于是回来的 ACK
   少一个数量级 —— 而每个 ACK 都是栈必须处理的一个包。**这部分优势来自 I/O 批量化，
   不是协议代码本身。** 就算按「每个数据包」而不是「每个包」归一化，smoltcp 仍是
   2.59 µs vs lwIP 10.5 µs，还是 4 倍，所以结论方向不变，但归因要说清楚。

### smoltcp 的硬伤：没有 catch-all 端口监听

**这是它能不能进生产的唯一拦路虎，比性能重要。** smoltcp 的 `IpListenEndpoint` 可以
`addr: None`（任意目的 IP，对应 lwIP 的 accept-all 补丁），但 **port 必须是具体值** ——
没有 lwIP 那种 `local_port == 0` 的通配分支。透明网关要接管的是设备发往**任意 (IP, 端口)**
的连接，这个能力是刚需，不是可选项。

三条出路，代价递增：

1. 给常用端口预挂监听（本跑分就是这么做的，只挂了 5201/5202）—— **生产不可行**，
   65535 个端口 × 每个 socket 两块 128 KiB 缓冲 = 荒谬的内存。
2. 改 smoltcp 的 socket 派发逻辑，加一个通配监听分支 —— 与我们在 lwIP 上打 accept-all
   补丁是同一类工作量，且 smoltcp 的 dispatch 比 lwIP 的 `tcp_in.c` 干净得多。**推荐这条。**
3. 每来一个新目的端口就动态建监听 socket —— 有 SYN 竞态窗口，且第一个 SYN 必丢。

另两个待确认项（都还没量，别当成结论）：

- **多设备/高并发下的表现。** 本轮是单条流。smoltcp 的 socket 是预分配固定池，
  几千条并发连接下的内存和查表成本还没测。lwIP 那边的已知崩溃场景（DNS 洪水 +
  并发 TCP 打崩 lwIP assert）也还没在 smoltcp 上复现过 —— **这才是换栈最初的动机之一**，
  下一轮必须补上。
- **Windows / macOS 可用性。** smoltcp 是纯 sans-io 的，不依赖任何平台设施，理论上
  三端通吃；但 `phy-tuntap_interface` 是 Linux-only 的便利封装，另外两端要自己接
  Npcap / BPF。这部分是工程量不是风险。

### 排查记录（三个坑，每个都「看起来完全不像是栈的锅」）

1. **`any_ip` 单开不够**：smoltcp 收到「不是发给我的」IP 包时还要过一道
   `routes.lookup(dst)`，而且判据是**查出来的下一跳必须是本栈自己的地址**
   （`ipv4.rs`：`.map_or(true, |router_addr| !self.has_ip_addr(router_addr))`）。
   所以默认路由的网关要填**自己**，填对端会被判成「非本地路由」照样丢。
   症状：ARP 通、ping 通、TCP 全超时，**零日志**。
2. **不能用 `may_recv()` 判设备是否发了 FIN**：它在 `SynReceived` 阶段同样是 false，
   照它判的话连接刚建好就把上游写端 shutdown 掉。症状：iperf3 报
   "unable to receive cookie" / "Connection reset by peer"，而栈进程活得好好的、
   **CPU 占用是 0.00**，怎么看都不像它的问题。正确做法是只看状态机
   （`CloseWait | LastAck | Closing | TimeWait | Closed`）。
3. shell 里 `setsid X &` 之后再 `wait`，会一直等那个永不退出的栈进程 ——
   验证脚本因此挂死 5 分钟。要 `wait` 就只 wait 具体的 PID。

**尚未测**：D（libslirp）/ E（内核栈）；smoltcp 的**并发与崩溃韧性**（比再多跑几个候选更重要）。

### R6 · 2026-08-03 20:54 UTC · 并发与内存 —— 单流的胜负在并发下还成不成立

单流已经分出胜负，这一轮量的是**并发下会不会翻盘**：`iperf3 -P {1,8,64}` 的吞吐曲线、
栈进程 RSS（空载 vs 64 并发）、600 条极短连接的连接风暴，以及每档跑完的存活检查。
三个栈依次跑，每次前置清理均验证机器空闲。

**并发吞吐 / 效率**

| 栈 | P=1 | P=8 | P=64 | 核/Gbps（P=1 → P=64） | P=64 重传 |
|---|---|---|---|---|---|
| lwIP | 1.136 | 1.072 | 0.997 Gbps | 0.879 → 1.008（**+15%**） | 10,032 |
| **smoltcp** | 4.560 | 4.639 | **4.087 Gbps** | **0.219 → 0.246（+12%）** | 19,051 |
| gVisor | 2.697 | 2.998 | 2.757 Gbps | 1.062 → 1.354（**+27%**） | 32,736 |

**内存 RSS（空载 → 64 并发）**

| 栈 | 空载 | P=64 | 增量 |
|---|---|---|---|
| lwIP | 6.6 MB | 7.3 MB | +0.7 |
| smoltcp | **4.1 MB** | 18.6 MB | +14.5 |
| gVisor | 8.3 MB | 25.2 MB | +16.9 |

**连接风暴（600 条建连→1 字节往返→关闭，串行）**

| 栈 | 成功 | 耗时 | CPU |
|---|---|---|---|
| lwIP | 600/600 | 0.13 s | 0.110 核·秒 |
| smoltcp | 600/600 | 0.10 s | 0.130 核·秒 |
| gVisor | 600/600 | 0.21 s | 0.310 核·秒 |

**三个栈全部存活，没有一个崩。**

结论：

- **smoltcp 的优势在并发下完整保持。** P=64 仍有 4.087 Gbps、0.246 核/Gbps，
  依然是 lwIP 的 4.1 倍效率。劣化幅度（+12%）也是三者里最小的。
- **gVisor 在并发下劣化最重**：效率掉 27%，重传是 smoltcp 的 1.7 倍、lwIP 的 3.3 倍。
  它的吞吐在 P=8 见顶（2.998）后回落，说明单 TAP fd 的收包路径已经是瓶颈。
- **lwIP 并发下吞吐还倒退**（1.136 → 0.997），单核本来就满，并发只是把同一份 CPU
  切得更碎。

#### 两个被证伪的猜测（都是我自己在 R5 里写下的担忧）

**① 「smoltcp 预分配缓冲会吃内存」—— 不成立。**
banner 自报 `backlog=64 prealloc=32MiB`（64 监听 × 2 端口 × 2×128 KiB），但**空载 RSS 只有
4.1 MB，比 lwIP 的 6.6 MB 还低**。原因是 `vec![0u8; N]` 走 calloc，页不碰就不落地；
RSS 只跟着**实际用到**的连接涨。同样在 64 并发下，smoltcp 18.6 MB < gVisor 25.2 MB。
**「预分配」是虚拟地址空间的事，不是常驻内存的事**——R5 里那句担忧可以划掉。

**② 「backlog 是并发上限」—— 也不成立，它是突发容忍度。**
用 `SMOL_BACKLOG=1` 重跑 P=64：照样跑通，3.788 Gbps、600/600 短连接全成功。
因为监听 socket 一被占用就在同一轮 poll 里补位，backlog 决定的是「两次 poll 之间能接住
几个 SYN」。代价只是吞吐 -7%、重传 +16%。**真正的并发上限是内存，不是这个数。**

#### 必须说明的：这一轮**没有**测到崩溃韧性

换栈的原始动机之一是 lwIP 在「单设备 DNS 洪水 + 并发 TCP」下必崩 assert
（见 [gateway-dns-flood-crash]）。**本 harness 是纯 TCP 的，复现不了那个配方**——
三个栈全部存活这件事，只能说明「64 路并发 + 600 次连接风暴打不垮它们」，
**不能**说明 smoltcp 在混合负载下比 lwIP 稳。这项仍然是空白，而且它比再多跑
一个候选重要得多：**如果 smoltcp 在那个配方下也崩，前面所有性能数字都不改变结论。**

**尚未测**：混合负载（UDP 洪水 + TCP）下的崩溃韧性 ← 最高优先级；D（libslirp）/ E（内核栈）。

### R7 · 2026-08-03 21:00 UTC · 崩溃韧性（混合负载）—— 一个把问题本身推翻的反结果

这是 R5/R6 一直标成「最高优先级」的那一项：lwIP 的原始动机之一是它在
「单设备 DNS 洪水 + 并发 TCP」下会撞 assert（见 [gateway-dns-flood-crash]）。
配方：TCP（`iperf3 -P 8`）全程在跑，DNS 形状的 UDP 洪水盖在上面，逐级加压。
洪水发生器自报实际 pps（"跑了洪水" ≠ "打到了量级"，没有计数器一次 EAGAIN 空跑会被
误读成"扛住了"）。

**TCP-under-flood（洪水期间 TCP 还剩多少吞吐，Gbps）**

| 栈 | 无洪水基线 | 20k pps | 100k pps | 400k pps | 洪水后恢复 | 崩了吗 |
|---|---|---|---|---|---|---|
| lwIP | 1.142 | 1.093 | 1.010 | 0.749 | 1.095 | **没有** |
| smoltcp | 4.739 | 4.466 | 3.503 | 1.307 | 4.704 | **没有** |
| gVisor | 2.967 | 2.791 | 2.315 | 0.927 | 2.909 | **没有** |

三档洪水的**实际** pps 都打满了目标（19999 / 99997 / 399987），不是空跑。
三个栈全部存活、洪水停后全部恢复到基线。

再加码：**分片大包**专打 IP 重组路径（2000~3000 B UDP，内核必分片，栈要重组——
这才是 OOSEQ/reassdata assert 的形状），rate 冲到实测 ~460k pps：

| 栈 | 200k×2000B | 500k×2000B | 800k×3000B | 重组洪水下 TCP | 结局 |
|---|---|---|---|---|---|
| lwIP | alive | alive | alive | 0.728 Gbps | **alive** |
| smoltcp | alive | alive | alive | 1.202 Gbps | **alive** |

**没有一个栈崩。包括 lwIP。**

#### 这个反结果比「smoltcp 赢了」更重要

我原本要证的命题是「smoltcp 能扛住打崩 lwIP 的负载」。但**这个 harness 打不崩现在的
lwIP**，所以命题的前提当场塌了——它没证明 smoltcp 更稳，而是**推翻了「换栈是为了躲崩溃」
这个动机本身**。两个原因，都得写清楚：

1. **本仓库的 lwipopts 早就是加固过的**：`IP_REASS_MAX_PBUFS=64`、`MEMP_NUM_REASSDATA=16`、
   `PBUF_POOL_SIZE=2048`、`MEMP_NUM_TCP_PCB=4096`——[gateway-dns-flood-crash] 那次崩溃的
   修法就在这些值里。**当年崩的是没加固的配置，不是 lwIP 本身没救。** 拿加固后的 lwIP
   当基线，"崩溃"这条动机已经被我们自己早先的工作消掉了大半。
2. **本 harness 的洪水走的是「无 UDP 监听者 → ICMP 端口不可达」路径**，不是生产里
   「DNS 真的被转发进 mihomo 的解析器」那条。两者压的池子不完全一样。所以**严格说，
   R7 既没能证伪 lwIP 会崩，也没能证明 smoltcp 不会崩**——它只证明了「加固配置 + 这个
   具体配方」三个栈都扛得住。真实生产配方的复现留给真机（Pi 网关台）。

诚实结论：**崩溃韧性不再是换栈的有效理由**，至少在当前加固配置下拿不出「lwIP 会崩而
smoltcp 不会」的证据。换栈的理由只剩一条，但很硬：**单核吞吐 4.1 倍 + 每 Gbps 便宜 4.1 倍**
（R5/R6）。决策应当完全建立在性能上，不要再引用"更稳"——那是一张兑不出的支票。

一个有用的副产品：**洪水期间的吞吐保持率就是抗 DoS 能力的代理指标**。400k pps 下 TCP
残余吞吐 lwIP 保 66%、smoltcp 保 28%、gVisor 保 31%——**lwIP 的每包处理更省，反而在
洪水下把 CPU 更多留给了 TCP**。这与"smoltcp 每包更快"不矛盾：smoltcp 的快来自批量化
I/O（R5 的 GRO 那段），而洪水是逐包 ICMP、批量化用不上，于是 smoltcp 单包处理的固定成本
在这种最坏负载下反而吃亏。**这是 lwIP 在整个测试里唯一赢过 smoltcp 的一项，值得记住。**

**尚未测**：真机（Pi 网关）上的生产级 DNS 转发洪水配方；D（libslirp）/ E（内核栈）。

### R8 · 2026-08-03 21:11 UTC · smoltcp 的 catch-all —— 把 R5 那张"推荐"的空头支票兑现

R5 把 smoltcp 唯一的硬伤（没有 catch-all 端口监听）标成了进生产的拦路虎，并写了句
「推荐改 smoltcp 派发逻辑加通配分支」——**但那是没验证的空话**。这一轮把它做出来并证明可行。

**做法：不 fork smoltcp，在 phy 层加一个端口改写 shim**（`catchall.rs`，~150 行）。
包装 smoltcp 的 `Device`：

- **RX（设备→栈）**：把 TCP 目的端口改写成一个固定端口 `FIXED_PORT`，用
  `(客户端IP, 客户端端口, 服务IP) → 真实目的端口` 记进一张表。栈这边**只挂一个**
  `addr:None, port=FIXED` 的监听，就接住了所有端口。
- **forwarder**：连接的 `local_port` 恒为 FIXED，查表拿回真实目的端口，据此连上游。
- **TX（栈→设备）**：把源端口从 FIXED 改回真实目的端口，设备看到的回包就来自真实 (IP,端口)。
- **校验和**：只动 16 位端口，用 RFC 1624 增量修正，不做全量重算。

这比 fork smoltcp 更轻（零改动它的源码），也比 R5 设想的"改派发逻辑"更干净。

#### 证明：一个监听，接住任意端口

单个 `FIXED_PORT=1` 监听，同时连三个不同目的端口的靶：

| 目的端口 | 靶 | 结果 |
|---|---|---|
| 5201 | iperf3 | **OK**（收到 banner） |
| 5202 | echo | **OK**（`ping` 原样返回） |
| 7777 | echo | **OK**（`ping` 原样返回） |
| 9999 | 无靶 | **正确拒绝**（上游 connect 失败 → abort → 客户端收 RST） |

前三个走的是**同一个** smoltcp 监听 socket，被 shim 分别改写又还原。9999 无靶时正确地一路
拒绝到底（不是黑洞、不是崩溃），说明失败路径也对。

#### 性能：shim 几乎不要钱

| smoltcp 变体 | 吞吐中位 | 核 | 核/Gbps | p50 | p99 |
|---|---|---|---|---|---|
| 直连（固定端口监听） | 4.636 Gbps | 1.00 | 0.215 | 0.076 ms | 0.096 ms |
| **catch-all（端口改写 shim）** | **4.408 Gbps** | 1.00 | 0.227 | 0.081 ms | 0.111 ms |

**catch-all 只掉 4.9% 吞吐、每 Gbps 贵 5.6%、延迟 p99 +15 µs。** 代价来自 RX 那一侧
`consume` 拿到的是 `&[u8]` 不可变、必须先 `to_vec()` 拷一份再改（smoltcp 0.12 的
`RxToken` 语义所限）——真正落地时可以让 TAP 读进一块可写缓冲直接原地改，这 4.9% 还能拿回来。
即便按现在这个未优化版本，**它仍是 lwIP 的 3.85 倍吞吐、每 Gbps 便宜 3.85 倍**。

#### 这一轮把决策钉死了

| 栈 | 吞吐 | 核/Gbps | catch-all | 崩溃(加固后) | 结论 |
|---|---|---|---|---|---|
| lwIP | 1.13 Gbps | 0.883 | ✅ 已有 accept-all 补丁 | 不崩 | 现状，单核封顶 |
| gVisor | 2.61 Gbps | 1.089 | ✅ promiscuous+spoofing | 不崩 | 贵且延迟差，只赢在多核 |
| **smoltcp** | **4.41–4.64 Gbps** | **0.215–0.227** | ✅ **本轮已实现（shim）** | 不崩 | **全面最优** |

smoltcp 的两个"未知数"到此清零：catch-all 能做（本轮），崩溃韧性不输 lwIP（R7）。
它在**吞吐、每 Gbps CPU、延迟、内存**上全面领先，唯一弱项是最坏 ICMP 洪水下的吞吐保持
（R7，且那是 DoS 边缘工况）。**替换 lwIP 的候选就是 smoltcp，理由是单核 ~4 倍吞吐，
且换栈不引入 catch-all 或稳定性的退步。**

剩下的都是工程落地、不是选型问题：把 shim 的 RX 拷贝去掉、接 Npcap/BPF 让三端可用、
把 smoltcp 接进 `NetStack` 的 `IL2Endpoint` 抽象、真机（Pi 网关）跑生产级混合流量复验。

**尚未测（但已不影响选型）**：真机生产配方；shim 去拷贝后的性能；D（libslirp）/ E（内核栈）
——后两者在单核效率上已无可能赢过 smoltcp，除非有非性能理由，否则不必再跑。

### R9 · 2026-08-03 21:16 UTC · 兑现 R8 的第二张支票：去掉 shim 的拷贝

R8 结尾又写了句没验证的预测：「那 4.9% 的开销全在 RX 那次 `to_vec` 拷贝上，真正落地让
TAP 读进可写缓冲原地改就能拿回来」。这一轮把它做出来验证——**不验证的乐观预测在这个
探索里已经栽过好几次**（见 R4/R6/R7 那几个被自己证伪的判断），不能留着。

做法：写一个自带改写的原始 TAP 设备 `rawtap.rs`（~110 行），自己管 fd，
RX 读进一块**复用**缓冲后原地改写（省掉 `to_vec`），TX 让 smoltcp 写进复用缓冲后原地改回。
改写逻辑（查表 + RFC 1624 校验和）与 R8 完全共用，唯一变量就是那次拷贝。

catch-all 仍成立（5201 iperf3 + 5202 echo 走同一个 FIXED 监听均 OK），三轮：

| smoltcp 变体 | 吞吐中位 | 核/Gbps | p50 | p99 |
|---|---|---|---|---|
| 直连（smoltcp 自带 TunTapInterface） | 4.636 Gbps | 0.215 | 0.076 ms | 0.096 ms |
| catch-all shim（R8，有 to_vec） | 4.408 Gbps | 0.227 | 0.081 ms | 0.111 ms |
| **catch-all 原地改写（本轮）** | **4.766 Gbps** | **0.210** | 0.089 ms | 0.102 ms |

**预测兑现，而且超额：4.9% 不但全部拿回，还净赚了 —— 原地版比连 shim 都没有的直连版
还快 2.8%。**

为什么会**倒赚**：`rawtap.rs` 顺手干掉了 smoltcp 自带 `TunTapInterface` 的一个隐藏开销——
它**每收一个包 `vec![0; mtu]` 分配一次**（读它的源码确认过）。我的 RawTap 用一块固定缓冲
复读复写，把这个每包 malloc 也省了。所以原地版赢的不只是 shim 那次拷贝，还有 smoltcp
默认 phy 层的每包分配。**这条对生产落地是白捡的：自己写 phy 层本来就是必须的
（要接 Npcap/BPF），顺带就把 smoltcp 的默认分配开销也绕过了。**

于是 catch-all 的最终账：**不但零成本，还倒赚 2.8%**。R8 表里「shim 掉 4.9%」这个数
只属于「偷懒复用 smoltcp 自带设备」的中间版本，真正落地的数是这一行 4.766 Gbps /
0.210 核/Gbps —— **lwIP 的 4.2 倍吞吐、每 Gbps 便宜 4.2 倍，且自带 catch-all**。

### 最终选型表（9 轮，全部同机同 harness，每轮前置清理验证空闲）

| 栈 | 吞吐 | 核/Gbps | p99 延迟 | catch-all | 加固后崩溃 | 相对 lwIP |
|---|---|---|---|---|---|---|
| lwIP（现状） | 1.13 Gbps | 0.883 | 0.121 ms | ✅ accept-all 补丁 | 不崩 | 基准 |
| gVisor | 2.61 Gbps | 1.089 | 0.174 ms | ✅ promisc+spoof | 不崩 | 快但贵 |

**结论已终局：用 smoltcp 替换 lwIP。** 单核吞吐 4.2 倍、每 Gbps CPU 便宜 4.2 倍、延迟略优、

### R10 · 2026-08-03 21:21 UTC · 小对象/短连接 —— 把 R9「终局」结论打回重开

前 9 轮的吞吐**全是单条 iperf bulk 流**。这是贯穿整个探索的系统性盲点：真实网关流量是
「连上→拿一个几十 KB 的对象→关闭」的海量短连接，而 R5 已经查明 smoltcp 的一大截优势
来自 GRO 批量合并——GRO 只在长流上生效。所以必须测小对象。32 并发 worker，各自
connect→读完固定大小对象→close 死循环，跑 8 秒，量 **完成对象数/秒**。

| 栈 | 4 KiB 对象 | 64 KiB 对象 | 1 MiB 对象 |
|---|---|---|---|
| **lwIP** | **6907 obj/s** | **2602 obj/s** | 93 obj/s |
| smoltcp（R9 落地形态） | **120 obj/s**（2366 错误） | 105 obj/s | 73 obj/s |
| gVisor | 396 obj/s | 372 obj/s | 88 obj/s |

**smoltcp 在最典型的网页负载（4 KiB 对象）上只有 lwIP 的 1.7%，还伴随大量连接错误。**
单流 4× 领先在这里彻底翻转成落后 57×。gVisor 也退化但没崩。

#### 根因排查：不是 smoltcp 协议慢，是集成方式的两个洞

现象诡异得可疑：无论 backlog（64/512/2048）还是 workers（1/4/32），成功数**恰好都是 1020**。
1020 ≈ 1024 = **文件描述符默认上限**，这是硬墙不是速率。抬 `ulimit -n`：

| ulimit -n | 成功对象 | 错误 |
|---|---|---|
| 1024 | 1020（撞墙） | 2366 |
| 262144 | 3163 | 32 |

**洞 ①（已根因）：forwarder 在 smoltcp 的 TIME_WAIT 期间一直攥着上游内核 fd。**
我的 smoltcp forwarder 只在 smoltcp socket 走到 `State::Closed` 才 drop `Conn`（连同它持有的
上游 `TcpStream`），而 smoltcp socket 要在 TIME_WAIT 里停几秒。高频短连接下，每秒新建的
连接 × TIME_WAIT 秒数 = 同时攥住的 fd 数，1024 个 fd 秒满，之后每个 connect 都失败。
**对照：lwIP 在 ulimit=1024 下照跑 6907 obj/s——它拆完连接立刻关上游 fd，不攥。** 这是
我 smoltcp 集成的 naïve 之处，不是 smoltcp 库的问题（fd 生命周期是我的代码决定的）。

**洞 ②（未根因，但真实）：即便 fd 不设限，smoltcp 也只有 583 obj/s，仍是 lwIP 的 1/12。**
抬到 ulimit=262144 后 fd 不再是瓶颈，可吞吐只回到 583 obj/s，离 lwIP 的 6907 还差一个数量级。
最可疑的是**成千上万个 TIME_WAIT socket 堆在 `SocketSet` 里，让每次 `iface.poll()` 变成
O(n) 扫描**，把新连接的处理能力压死。这条还没坐实，但方向明确——smoltcp 的 sans-io 模型
把 socket 生命周期全压在用户这边，短连接海量 churn 正是它最不趁手的形状。

#### 对选型的影响：R9 的「终局」作废，结论重开

**bulk 吞吐和短连接吞吐是两个独立的胜负手，smoltcp 各赢一个、输一个：**

| 负载形状 | 赢家 | 差距 |
|---|---|---|
| 单条长流（下载/视频/大文件） | smoltcp | 4.2× |
| 海量短连接小对象（网页浏览） | **lwIP** | **57×** |

真实网关两种流量都有，而且**短连接是更常见的日常形状**。所以不能再说「smoltcp 全面最优」。
诚实的当前结论：

1. **smoltcp 的 4× 只在 bulk 负载成立**，短连接下它现在的集成形态是灾难。
2. 短连接的两个洞**至少洞①是明确可修的**（forwarder 拆连接时立刻关上游 fd，别等 TIME_WAIT；
   或给 smoltcp socket 装 TIME_WAIT 主动回收）。修完必须**重测**才知道能不能追平 lwIP。
3. 洞②（poll 的 O(n)）若坐实，可能需要给 smoltcp 的 SocketSet 换更快的查找结构，或限制
   lingering socket 数——工作量和不确定性都比洞①大。
4. **在洞①②修复并重测证明短连接不输 lwIP 之前，不能选 smoltcp 替换 lwIP。** lwIP 现状在
   短连接上反而是三个栈里最好的——这也解释了为什么它一直够用。

这一轮是整个探索的方法论在打自己脸：前 9 轮用一个 bulk 指标就敢写「终局」，正是这个
探索反复警告的「测了 ≠ 测全了」。**R9 的收敛是假收敛。**

**下一轮必做**：修洞①（forwarder 早关上游 fd），重跑 R10 的小对象负载，看 smoltcp 能否
从 120 obj/s 追上 lwIP 的 6907；追不上就查洞②。**这是选型能否落地的真正关口，比三端 phy
移植优先级更高。**

> ✅ **R11 已修复并重验证——洞①②同源，一并根治，smoltcp 结论恢复。** 见下。

### R11 · 2026-08-03 21:33 UTC · 修 forwarder，短连接翻案 —— 两个洞本是同一个根

R10 把「smoltcp 短连接崩」归到两个洞（fd 泄漏 + poll O(n)）。修法只动 forwarder，不碰 smoltcp：

1. **`Conn.up` 改成 `Option<TcpStream>`**：上游读到 EOF 且下行已全部灌给设备，就**立刻**
   `take()` 掉关 fd，与 smoltcp socket 的 TIME_WAIT 解耦（原来要等 `State::Closed`，几秒后的事）。
2. **smoltcp socket 走到 `TimeWait` 就 `sockets.remove()`**，不空等 2·MSL 定时器——到 TimeWait
   说明最后一个 ACK 已发出，提前回收安全，且不让 TIME_WAIT socket 堆在 SocketSet 里。

重跑 R10 的小对象负载（同机同 harness）：

| 栈 | 4 KiB | 64 KiB | 1 MiB |
|---|---|---|---|
| lwIP | 6907 obj/s | 2602 | 93 |
| smoltcp（R10 崩溃版） | 120（2366 错误） | 105 | 73 |
| **smoltcp（R11 修复版）** | **6796 obj/s（0 错误）** | **2374** | **171** |

**从 120 追到 6796，追平 lwIP（98%），1 MiB 大对象反超 1.8×。每对象 CPU 144.5 µs 与 lwIP 的
144.4 µs 几乎一字不差——短连接下两者每对象成本已经等同。**

两个确凿的旁证，说明修复是真的、不是碰巧：

- **默认 ulimit=1024 下不再卡 1020**：6741 obj/s、**0 错误、峰值 fd 仅 4 个**。修复前是攥住
  1020 个 fd 撞墙；现在拆完连接立刻还 fd，稳态只占个位数。洞① 彻底消失。
- **洞② 也随之消失**——高 ulimit 下那个 583 obj/s 的天花板不存在了。证明洞②不是独立问题，
  就是同一批 TIME_WAIT socket 堆积的另一种表现，`TimeWait` 提前回收一并解决。
- **bulk 吞吐无回归**：4.759 Gbps（R9 是 4.766）。提前回收 TIME_WAIT 只影响短连接的 socket
  周转，不碰长流。

#### 选型结论恢复——但这次站在两种负载上，不是一种

R10 打回的是「只用 bulk 一个指标就下终局」。R11 补上了短连接这条腿，两条腿都验证过了：

| 负载形状 | lwIP | smoltcp（修复版） | 赢家 |
|---|---|---|---|
| 单条长流（下载/视频） | 1.13 Gbps | **4.76 Gbps** | smoltcp 4.2× |
| 短连接 4 KiB（网页） | 6907 obj/s | 6796 obj/s | **持平**（98%） |
| 短连接 1 MiB | 93 obj/s | **171 obj/s** | smoltcp 1.8× |
| 每对象 CPU（4 KiB） | 144.4 µs | 144.5 µs | 持平 |

**smoltcp 在 bulk 上大幅领先、在短连接上与 lwIP 持平（大对象还反超），没有一种常见负载
它输。** R10 的「输 57×」纯粹是我 forwarder 的 fd 生命周期写错，与 smoltcp 无关——lwIP 的
C forwarder 一开始就是早关 fd 的，这才是它短连接不崩的原因，现在 smoltcp forwarder 也这么做了。

**选型重新收敛到 smoltcp，且这次是真收敛**：bulk 4.2×、短连接持平、catch-all 零成本
（R8/R9）、崩溃韧性不输（R7）、内存更省（R6）。唯一弱项仍是最坏 ICMP 洪水下的吞吐保持
（R7，DoS 边缘工况），已知且可接受。

方法论收尾：R9 假收敛 → R10 用短连接证伪 → R11 根因是 forwarder 不是 smoltcp、修好重验 →
真收敛。**这一来一回正是「测了 ≠ 测全了」的价值：如果当初 R9 就拍板移植，会在真实网页
流量上踩到 57× 的坑；而如果 R10 就此判 smoltcp 死刑，又会错杀一个其实只是集成 bug 的好方案。**

**剩余全是工程落地**：三端 phy（Npcap/BPF/AF_PACKET）、接进 `NetStack` 的 `IL2Endpoint`、
Pi 网关 ARM 真机复验（唯一没覆盖的架构维度，Pi 当前不可达）。选型部分到此**真正**收敛。

### R12 · 2026-08-03 21:40 UTC · bulk 打满时的交互延迟（队头阻塞）—— 三方各有取舍

前面所有延迟数都是**空载**测的。真实网关体验的关键却是「一个大下载正在跑，网页点击还
秒不秒回」。单线程 poll 的栈尤其可能在这翻车。做法：后台 `iperf3 -P4` 灌满，前台同时打
100 次 1 字节乒乓，量 bulk 期间的往返分布。

（ARM 维度本想这轮补——Pi `.92`/`.34` 关机、mac `.14` 在线但 batch SSH 认证过不去，且
smoltcp 的 `phy-tuntap_interface` 是 Linux-only，移到 macOS BPF 属落地工程不属跑分。
ARM 复验仍挂着，等 Pi 上线。这轮改测这个更该测、且能干净测的维度。）

| 栈 | bulk 期间往返 p50 | p90 | p99 | **max** | mean | 同时 bulk 吞吐 |
|---|---|---|---|---|---|---|
| lwIP | **0.078 ms** | 0.086 | 0.173 | **11980 ms** | 120 ms | 1.09 Gbps |
| **smoltcp** | 1.27 ms | 1.335 | 1.60 | **1.71 ms** | 1.28 ms | **5.01 Gbps** |
| gVisor | 3.46 ms | 3.94 | 4.25 | 4.82 ms | 3.39 ms | 3.04 Gbps |

**这是整个探索里最需要小心解读的一组数——没有一个栈全赢：**

- **lwIP 的中位延迟近乎完美（0.078 ms，跟空载一样），但尾部是灾难：max 11.98 秒、
  mean 120 ms。** 双峰分布——约 99% 的请求瞬回，但**约 1% 卡好几秒**（R12 第一次跑就是
  这一下把 5 秒超时的探针打崩的，两次独立复现）。这是典型的 bufferbloat/饿死尖峰：
  bulk 的段偶尔把小请求的段压在后面几秒。**对体验来说，网页每一百次点击冻结一次十几秒，
  比稳定 1.3 ms 难受得多。**
- **smoltcp 中位higher（1.27 ms）但分布最紧、无灾难尾（max 1.71 ms）。** 而且它是在
  **同时推 5.0 Gbps**（lwIP 的 4.6 倍）的情况下守住这个有界延迟的。可预测性完胜。
- **gVisor 中位最差（3.46 ms）但有界**，吞吐居中。

结论对选型的意义：**「延迟」这一栏不能再简单写"smoltcp 略优"（那是空载结论，R2）。
负载下真相是——lwIP 中位更好但会甩多秒尖峰，smoltcp 牺牲一点中位换来有界可预测 +
4.6× 吞吐。** 对透明网关（多人共享、忌讳卡顿）而言，smoltcp 那种「稳定 1.3 ms」的曲线
是更好的产品形态，lwIP 的「大部分飞快、偶尔冻十秒」反而是投诉来源。这条**加强**了选
smoltcp 的理由，但理由从「延迟更低」修正为「负载下延迟有界、且不牺牲吞吐」。

（题外：lwIP 的尖峰可能靠调 TCP pacing / 减小 bulk 在 socket 缓冲的堆积来压，但那是给
lwIP 续命的调优，不改变 smoltcp 已在「有界延迟 + 4.6× 吞吐」上整体领先的事实。）

**尚未测**：ARM 真机（Pi 上线后补，唯一架构盲点）；三端 phy 落地后的端到端。
选型结论不变：**smoltcp**，且 R12 让「负载下体验」这一维也倒向它。

### R13 · 2026-08-03 21:56 UTC · UDP 转发（QUIC/HTTP3 的形状）—— lwIP 在这一项反赢

**前 12 轮全是 TCP。** 而真实网关约三成流量是 UDP：QUIC(HTTP3)、DNS、视频。给两个栈
都加上 UDP 转发（固定端口单流，与 R5 的 TCP 直连同思路），用自定义 UDP echo 打（不用
iperf3，因为 `iperf3 -u` 仍要一条同端口 TCP 控制连接，会把 TCP 路径混进来）。

两栈各约 1 核，单流，三种包长：

| 栈 | 64 B rx_pps | 512 B rx_pps | 1400 B | 丢包率 | 每数据报 CPU |
|---|---|---|---|---|---|
| **lwIP** | **136905** | **124047** | **1.312 Gbps** | 3.6~4.5% | **6.9 µs** |
| smoltcp | 91057 | 83582 | 0.841 Gbps | 6.6~8.0% | 10.3 µs |

**UDP 上 lwIP 反赢——pps 高约 1.5×、丢包只有 smoltcp 的一半、每数据报便宜 1.5×。
这和 TCP 完全相反（TCP bulk smoltcp 赢 4×）。**

原因清楚：**UDP 是逐数据报的，没有 TCP 那种批量化/GRO 可吃**（smoltcp 4× 的一大来源，
见 R5）。lwIP 的 UDP 路径是一个 `udp_recv` 回调直接转发，极瘦；smoltcp 的 UDP 走
`PacketBuffer` + 每数据报一条 metadata + 还要过 phy 层那个（对 UDP 是空操作但仍执行的）
改写 shim。逐包场景下 smoltcp 的固定开销摊不掉，反而吃亏——和 R7 洪水下 lwIP 每包更省
是同一个道理。

对选型的意义：**这是 TCP 之外第一个 lwIP 明确赢的负载，且赢在正在快速增长的 QUIC 上。**
但它不推翻结论，原因有三：

1. **量级仍是可用的**：smoltcp UDP 单核也有 9 万 pps / 0.84 Gbps，对家用网关的 QUIC/DNS
   量足够；差距是「更好 vs 够用」，不是「行 vs 不行」。
2. **吞吐大头仍是 TCP**：大文件/视频流即便走 QUIC 也是长流，长流的每字节成本 smoltcp 仍
   可能靠聚合追回（本轮是小数据报最坏情形，没测 QUIC 长流）。
3. **smoltcp 的 UDP forwarder 是本轮临时写的、没调优**（多过一层 shim、每报一次 metadata）；
   给 UDP 走一条绕开 shim 的专用路径，多半能收窄这 1.5×。属落地可优化项。

诚实修正：选型总账从「smoltcp 全面领先」修正为**「smoltcp 在 TCP（吞吐/延迟/短连接）全面
领先，lwIP 在 UDP 逐包上更省」**。对以 TCP 为主的网关，smoltcp 仍是正解；若目标流量
QUIC 占比很高，则要么优化 smoltcp 的 UDP 路径、要么重新权衡。

#### 一个真实的集成陷阱（记下来，落地 UDP 网关会撞）

lwIP 的 UDP 回包必须用 `udp_sendto_if_src()` 显式传源 IP，**不能**用 `udp_sendto`/
`udp_sendto_if`：后者有一道检查——源 IP 不等于 netif 自己的地址就返回 `ERR_RTE(-4)` 丢包
（`udp.c`：「local_ip doesn't match, drop the packet」）。而透明网关回包的源 IP 恰恰是
「原始目的 IP」、不是本机地址，必撞这道墙。症状：设备→上游全通（echo 靶收到全部包）、
但回包一个都不出栈、100% 丢包、且**没有任何错误日志**（err 码被吞在转发循环里）。
排查靠的是 tcpdump 看方向 + strace 数 echo 靶的 recvfrom + 给 sendto 返回值加打印。

**尚未测**：ARM 真机（唯一架构盲点，Pi 关机、mac 台是 x86）；QUIC 长流（vs 本轮小数据报）；
smoltcp UDP 走专用路径去 shim 后的吞吐。选型主结论：**TCP 为主选 smoltcp，UDP 重则再权衡**。

### R14 · 2026-08-03 22:00 UTC · UDP 走裸 NAT 绕开栈 —— 把 R13 的短板反转成又一个赢

R13 结尾留了个 hedge：「smoltcp 的 UDP forwarder 没调优，走专用路径绕开 shim 多半能收窄
1.5×」。这又是个没验证的乐观预测——本探索栽过太多次（R8/R10/R13 的 item-3 都是我自己的
乐观判断），必须测。而且细想 R13 那个归因其实站不住：shim 对 UDP 本就近乎空操作
（`tcp_offsets` 见非 TCP 立即返回），真正的开销在 smoltcp 的 UDP **socket** 上（双拷贝 +
逐报 metadata + dispatch）。

正确的修法不是「优化 smoltcp 的 UDP socket」，而是**根本不让 UDP 走 smoltcp**——UDP 无连接，
不需要协议栈的任何状态机。标准 tun2socks 就是 TCP 走栈、UDP 走一张 NAT 表。实现（`natdev.rs`
~180 行）：phy 层拦下 UDP 帧，转到内核 socket，回包**手工造 eth+ip+udp 帧**（IP/UDP 校验和
自己算）直接写回 TAP，全程不碰 smoltcp。TCP 仍照常交给 smoltcp。

UDP 转发，单流约 1 核，与前两者同条件对比：

| 方案 | 64 B rx_pps | 512 B | 1400 B | 丢包 | 每数据报 CPU |
|---|---|---|---|---|---|
| smoltcp UDP-socket（R13） | 91057 | 83582 | 0.841 Gbps | 6.6~8.0% | 10.3 µs |
| lwIP（栈内 UDP） | 136905 | 124047 | 1.312 Gbps | 3.6~4.5% | 6.9 µs |
| **smoltcp + 裸 NAT（本轮）** | **145635** | **136711** | **1.378 Gbps** | 3.6~4.3% | **6.3 µs** |

**裸 NAT 一举把 UDP 从「落后 socket 版 1.6×」拉到「反超 lwIP +5~6%」，丢包降回 lwIP 水平，
每数据报还更省，而 TCP 照常通过（`b'hi'` 原样返回）。** R13 的 item-3 预测不但对，而且不是
「收窄」是「反超」。

#### 这条彻底消除了 R13 的 UDP 保留意见

R13 曾把总账修正为「smoltcp 在 TCP 领先、lwIP 在 UDP 更省」。R14 证明那个 UDP 短板**不是
smoltcp 的固有缺陷，而是"让 UDP 去挤 socket"的集成错误**。正确架构下：

| 负载 | lwIP | **smoltcp + UDP-NAT** | 赢家 |
|---|---|---|---|
| TCP 单条长流 | 1.13 Gbps | 4.76 Gbps | smoltcp 4.2× |
| TCP 短连接 4 KiB | 6907 obj/s | 6796 obj/s | 持平 |
| TCP 负载下延迟 | 中位好但甩 12s 尖峰 | 有界 1.3 ms | smoltcp（体验） |
| **UDP 逐数据报** | 136905 pps | **145635 pps** | **smoltcp +6%** |
| 内存 | 6.6 MB | 4.1 MB | smoltcp |

**现在没有一种负载 lwIP 赢。** 最终架构定型：**TCP 交给 smoltcp（catch-all 靠 phy 端口改写
shim）、UDP 交给 phy 层裸 NAT**——两者共用同一个 RawTap/NatTap 设备、同一个 TAP fd。这正是
成熟 tun2socks 的通行结构，本探索用数据独立推到了同一个设计。

方法论收尾（本探索反复的主题）：R13 我给 UDP 短板留了个「大概能优化」的 hedge，R14 逼自己
把它测了——结果不是小修小补，是换对了架构后直接反超。**留 hedge 不测，就会把一个架构选择
错记成一个能力短板。**

**尚未测（不影响选型）**：ARM 真机（唯一架构盲点，Pi 关机、两台 mac 均 x86）；QUIC 长流；
NAT 表在数千并发 UDP 流下的老化/内存。**选型到此全维度收敛：TCP+UDP 都是 smoltcp(+NAT) 方案更优。**

### R15 · 2026-08-03 22:08 UTC · NAT 表在海量 UDP 流下崩溃 —— R10 的 bug 我又犯了一遍

R14 末尾我把「NAT 表在数千并发流下的老化/内存」列为「不影响选型」的待测项。**这是偷懒**——
一台设备猛开 QUIC 就是几千条并发 UDP 流，而我 R14 的 `natdev.rs` flow map **从不淘汰、
建 socket 还 `unwrap()`**。这跟 R10 那个 TCP fd 泄漏是同一类 bug，而且我在 R11 明明「学到」
了教训，转头在 R14 的新代码里原样又犯一遍。测试：`udpmany` 制造 2 万条不同源端口的 UDP 流。

| 栈 | 2 万流后 fd | RSS | 存活 |
|---|---|---|---|
| smoltcp + NAT（R14 原版） | — | — | **崩溃（core dumped）** |
| lwIP | 5 → 261 | 6.6→6.8 MB | 活（但静默丢弃第 256 条之后的流） |

smoltcp-NAT 直接 `panic`：`natdev.rs:90 UdpSocket::bind().unwrap()` → `Too many open files`
（errno 24）。2 万条流 = 2 万个内核 socket，fd 耗尽，`unwrap` 把**整个网关**崩掉。比 R10 更
致命——R10 只是连不上，这里是进程死。lwIP 侥幸没崩，只因它的 harness 用了定长数组
`g_uflows[256]`，超了**静默丢流**（也不对，只是不崩）。**两边其实都漏，只是表现不同。**

#### 两级修复（照搬 R11，但比 R11 多一个坑）

**修 v1：flow 表加上限 `NAT_CAP` + FIFO 淘汰 + 永不 `unwrap`（EMFILE 就丢这条流）。**
结果：不崩了（5 万流存活），但**功能瘫痪**——洪水后新流 100% 丢包。根因是进程默认
`ulimit -n=1024` < `NAT_CAP=4096`，flow 数到不了 4096，FIFO 淘汰**永不触发**，1020 个 fd
全被死流攥着，新流 `bind→EMFILE→丢`。**从「崩溃」变成「卡死」，还是坏的。**

**修 v2：启动就 `setrlimit(RLIMIT_NOFILE, 65536)`**（真实网关守护进程本就该做），让 `NAT_CAP`
成为真正的界、FIFO 淘汰在撞 fd 墙前生效。重测 5 万流：

| | 修复后 |
|---|---|
| 存活 | **是** |
| fd 峰值 | **4100**（= NAT_CAP 4096 + 基础 fd，稳定不涨） |
| RSS | 3.1 MB（几乎不动） |
| 洪水中送达 | 143772 / 150000 = **96%**（原版崩前只 8445） |
| 洪水后新流 | 11% 丢包（原版 100%）——网关**恢复正常** |

现在 NAT 表在任意流数下都**有界**（4096 socket 封顶，FIFO 淘汰最老流并归还 fd），不崩不漏。

#### 方法论：这是整个探索最该记住的一轮

R15 没有改变选型（smoltcp+NAT 仍是答案），但它抓到一个**会直接崩溃生产网关**的真实 bug，
而这个 bug 是我**在已经吃过一次亏（R10/R11）之后、于新组件里重新引入的**。教训有三层：

1. **「不影响选型」不等于「不用测」**——R14 我用这个词把一个崩溃级 bug 推到了将来。
2. **每个新组件都要重新过一遍资源生命周期**，R11 学到的不会自动套用到 R14 的新代码。
3. **`unwrap()` 在网关热路径上等于埋雷**——同样是 fd 耗尽，`unwrap` 让它从「丢一条流」
   升级成「整个进程死」。落地时 natdev/lwip 两边的 NAT 表都得按真实老化（idle timeout）
   来管，本轮的 FIFO+CAP 是最低限度的止血。

**尚未测**：ARM 真机（唯一架构盲点）；QUIC 长流；NAT 的 idle-timeout 老化（本轮是 FIFO
近似）。**选型全维度收敛且 UDP-NAT 已加固：替换 lwIP 用 smoltcp(TCP)+裸 NAT(UDP)。**

### R16 · 2026-08-03 22:14 UTC · NAT 老化换成 idle-timeout —— FIFO 会误杀正在播的视频

R15 用 FIFO（按**创建顺序**淘汰）给 NAT 表止血，末尾又留一句「落地要按 idle-timeout」。
这个 hedge 底下藏着一个真 bug：FIFO 淘汰最老的流，而一条**长期活跃**的流（正在播的 QUIC
视频、一个持续的 VoIP 通话）恰恰是最老的——它会在流量正忙时被 FIFO 一脚踢开，而旁边一堆
刚建的死流反倒占着位置。换成正确的 **idle-timeout**：活动即 `touch`，只回收真正闲置超过
`NAT_IDLE` 的流；周期性主动扫（每 1s），不再等插入压力。

测法：一条**持久活跃流**（固定源端口，稳发 12 秒、全程计吞吐）跑在一场**洪水**（`udpmany`
造 3 万条不同短流，远超 `NAT_CAP=4096`）中间，看它会不会被淘汰，以及洪水停后 fd 回不回落。
`NAT_IDLE_MS=1500` 便于观察。

| 观测项 | 结果 | 说明 |
|---|---|---|
| 持久活跃流 12 秒 | **95493 rx_pps / 6.47% 丢包** | 全程存活，没被淘汰（6.47% 是与洪水抢单核，非淘汰） |
| 洪水中 fd 峰值 | **4100** | = NAT_CAP + 基础，有界不涨 |
| 进程存活 | 是 | |
| **洪水停 3 秒后 fd** | **4100 → 4** | 死流被 idle-timeout **主动回收**，fd/内存全还回来 |

两个关键点，都是 FIFO 给不了的：

1. **活跃流受保护**：新流满员时的退化淘汰用 `min_by last`（挑**最久未活动**的），持久流每
   ~10 ms 被 touch 一次，永远排在末尾、永不入选。FIFO 按创建序则会把它当「最老」淘汰——
   R16 证明 idle-timeout 下它稳稳活满 12 秒。
2. **闲置主动回收**：洪水停后 fd 从 4100 掉回 4。FIFO 只在**插入时**淘汰，洪水一停就没有新
   插入，那 4096 个死 socket 会一直攥着直到下一波流量才被顶掉；idle-timeout 的周期扫描则
   在 1.5 s 后主动把它们全关掉。对久经运行的网关，这是「fd/内存随峰值单调爬升」和「峰值
   过后回落」的区别。

至此 UDP-NAT 具备生产级的表管理：**上限有界（不崩）、活跃流不误杀、闲置流主动回收**。

方法论：R15 我把 idle-timeout 写成「以后再说」的 hedge，R16 测下来发现 FIFO 不只是「不够
精确」，是**会掐断正在进行的长连接**——一个 hedge 里藏着一个用户可感知的故障。**又一次
印证：留 hedge 不测，就把一个真 bug 记成了一句"待优化"。**

**尚未测（均不影响选型）**：ARM 真机（唯一架构盲点，Pi 关机、两台 mac 均 x86）；QUIC 长流
的字节吞吐（vs 本轮小报 pps）。**选型全维度收敛，两条数据面（smoltcp-TCP / 裸NAT-UDP）均已
churn 加固到生产级：替换 lwIP 用 smoltcp(TCP) + 裸 NAT(UDP)。**

### R17 · 2026-08-03 22:22 UTC · IPv6 —— 最后一个真选型风险（双栈漏代理）

前 16 轮全是 IPv4。而这个网关有个**文档级隐患**：双栈设备的 v6 流量若不被接管就会「漏代理」
（见 CLAUDE.md 的 NDP 投毒防线、[gateway] 那条）。lwipopts 早开了 v6 + ip6 accept-all 补丁；
smoltcp 这边我的 harness 一直是纯 v4（shim 只认 ethertype 0x0800、NAT 只处理 v4、Cargo 只开
`proto-ipv4`）。**若选 smoltcp，它到底能不能转发 v6，是必须回答的**——不测就是把「mature stack
大概支持」当结论，而本探索栽过太多这种。

做法：给 smoltcp 开 `proto-ipv6`，做一个双到 v6 的直连变体（`v6_main.rs`：v6 地址 fd99::2/64、
v6 any_ip、v6 默认路由 next-hop=自身、上游连 `::1`），把测试 v6 目的 `2001:db8::/32` 路由到栈。

| 检查项 | 结果 |
|---|---|
| NDP（邻居请求 NS → 通告 NA） | **自动通**（`ping6 fd99::2` 通，邻居 REACHABLE） |
| any_ip 收外部 v6 目的 | **通**（`ping6 2001:db8::5` 0% 丢包——非本机 v6 地址也接） |
| v6 TCP 转发（功能） | **通**（`v6hello` 经 catch-all 完整往返到 `::1` 又回来） |
| v6 TCP 吞吐 | **4.509 Gbps / 0 重传 / ~1 核** |

**smoltcp 的 IPv6 TCP 转发在功能和性能上都与 v4 等同**（4.5 vs v4 的 4.6~4.8 Gbps，同样单核）。
NDP、any_ip、catch-all 监听（`addr:None` 天然跨家族）全部开箱即用。**双栈漏代理这个最后的
选型风险，在栈层面清除了。**

一个复现坑（和 v4 的 ARP 首包丢是同一个）：v6 首包会在 NDP 邻居解析期丢，症状是
`No route to host`。第一次跑没预热就发 TCP，被这个假象骗了一下——**ping6 预热解析邻居后
一切正常**。别拿冷启动的第一个 v6 包判「不支持」。

诚实的剩余范围（都是工程、非选型）：本轮用的是**无 shim 的固定端口直连变体**，证明的是
smoltcp 的 v6 栈本身可用。生产的 `rt_main`（带端口改写 shim）和 `natdev`（UDP NAT）目前
**只解析 0x0800**，要覆盖 v6 得让 shim/NAT 也认 0x86dd（v6 头 40 字节定长、偏移不同）——
和 v4 是同一套代码换个 ethertype/偏移，是明确的工作量、不是未知风险。双栈同时跑（一网卡
v4+v6 并存）本轮也没测（只测了 v6-only）。

**选型维度到此全部覆盖**：吞吐 / 延迟（空载+负载）/ CPU / 并发 / 内存 / 崩溃韧性 / 短连接 /
UDP / NAT 老化 / **IPv6**。结论稳定：**替换 lwIP 用 smoltcp(TCP)+裸NAT(UDP)，v4/v6 双栈可行。**
**尚未测**：ARM 真机（唯一架构盲点，非功能风险）；v6 版 shim/NAT 与双栈并存（工程量，非选型）。

### R18 · 2026-08-03 22:30 UTC · 两条数据面同炉 —— 生产二进制的集成验证

前面 TCP（smoltcp）和 UDP（裸 NAT）都是**分开**测的。但真正要 ship 的 `nat_main` 里，两者
是**同一个进程、同一个 TAP fd、同一个 poll 循环**：`receive()` 先 drain UDP NAT，再把 TCP 帧
交给 smoltcp。它们会不会抢 TAP、把对方饿死、或在共享状态上串扰？这是分开测永远看不到的。

做法：`nat_main` 一个进程，`iperf3 -P4` 打 TCP（走 smoltcp，5201）与 `udpecho` 打 UDP（走
NAT，5203）**同时**满载。

| | 单独跑 | 同时跑 | 保留 |
|---|---|---|---|
| TCP | 4.739 Gbps | 1.618 Gbps | 34% |
| UDP | 141271 pps | 94822 pps（丢 6.4%） | 67% |
| 栈 CPU | — | ~1.1 核 | — |
| 存活 | — | **是（无崩溃、无串扰）** | — |

两条数据面**正确共存**——不崩、不乱、TCP 的 `b'…'` 和 UDP 的回包都对。混合下各自降速纯粹是
**单线程共享一个核**：一个 poll 循环在 smoltcp 和 NAT 间时间片轮转。UDP 保留 67% > TCP 的
34%，因为 `receive()` 里 UDP 先被 drain（隐含一点调度优先级）——真要 TCP 公平可调 drain 顺序。

关键判断：**即便混合切分后，1.6 Gbps TCP + 9.5 万 UDP pps 同时跑，仍高于 lwIP 单条数据面的
单核上限**（lwIP TCP 独占 ~1.1 Gbps、UDP 独占 ~124k pps）。也就是说 smoltcp+NAT 混合负载下的
「打折价」依然打平/优于 lwIP 的「单跑原价」。集成没有引入意外损耗。

若将来混合吞吐要突破单核，路径是现成的：多队列 TAP（`IFF_MULTI_QUEUE`）+ 每队列一个 poll
线程 / smoltcp 实例——gVisor 在 R3/R6 靠的就是多核，这条路 smoltcp 也能走，但当前单核已
4× 于 lwIP，非必要不上。

至此**连集成层面**都验过了：单进程双数据面、共享 TAP/poll、混合满载不崩不饿死。

**选型 + 数据面加固 + 全协议维度 + 集成，全部覆盖。** 唯一剩下的 ARM 真机是架构验证（Pi 关机），
不是功能或选型风险。**最终建议不变：替换 lwIP 用 smoltcp(TCP) + 裸 NAT(UDP)，单进程双数据面，
v4/v6 双栈可行，各资源面均已 churn 加固。**
