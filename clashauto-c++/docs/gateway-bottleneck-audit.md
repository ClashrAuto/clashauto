# 网关性能审计：到底堵在哪个环节（2026-08-04 重审）

> 起因：`lwip-alternatives.md` R19–R21 的结论是「Windows 网关的绑定约束是 **Npcap 发送路径**」。
> 那个结论**在当时是对的**（测的是 lwIP + Npcap）。但 lwIP 已经在今天被移除、smoltcp 成为唯一
> 数据面 —— 所以这次不看旧结论，从代码重新走一遍每个包的实际路径。
>
> **结果是绑定约束换人了** —— 但**只在低并发下**。第一版这里写成「不是 Npcap 了」，
> 那是**过早收敛**；第六节做了逐环节重审并修正：低并发泵量化、高并发仍是 Npcap，两个都真。

---

## 结论先行

| 环节 | 实测/推算上限 | 是不是今天的瓶颈 |
|---|---|---|
| **泵周期量化（25 ms）** | 📏 **≈21 Mb/s / 连接，上下行都是** | ★ **低并发下是**（见第六节修正） |
| **监听 backlog 32/拍** | 一拍最多 32 条新连接 | ★ 突发页面加载丢 SYN，每条多付 ~1s |
| ~~Npcap TX~~ | ~~📏 572 Mb/s ≈ 65k pps~~ | ❌ **已证伪，见第八节** —— 那是 QEMU e1000 模拟的顶，不是 Npcap 的顶 |
| smoltcp CPU | 📏 0.21 核/Gbps | 否 |
| 核心中继（DIRECT） | 📏 0.38 核/Gbps | 否 |

📏 = 实测。泵量化那一行来自本次新增的 `measure_realistic_upstream_ceiling`
（`rust/coaststack/src/e2e.rs`），可复现：`cargo test --release measure_realistic -- --nocapture`。

> ### ⚠️ 这个数被我改了三次，过程保留 —— 它本身就是结论的一部分
> 前两版都错，而且方向相反；第三版才收敛。
>
> | 版本 | 测法 | 结果 | 错在哪 |
> |---|---|---|---|
> | 1 | `measure_bytes_per_poll_cycle` | 41.9 Mb/s | 灌**出窗**数据 → 量到的是收缓冲容量(128 KiB)，不是设备被允许发的量。**偏乐观 2×** |
> | 2 | `measure_realistic_upstream_ceiling` | 20.6 Mb/s | 合成 SYN **不带 WS 选项** → 窗口缩放没生效，被 RFC 封在 65535。**前提错了，数字却撞对了** |
> | 3 | `measure_ceilings_with_window_scaling` | **20.8 / 21.0 Mb/s** | 带 WS。中途还踩了一次：对 SYN-ACK 的 window 套了 shift，而 **RFC 7323 规定 SYN 段的窗口不缩放** → 灌超量 → 假设备不重传 → 流停摆，量出个假的 "0.8 Mb/s" |
>
> ```
> [WS  ] SYN-ACK window=65535 shift=2 → 我方有效接收窗口 262140 B
> [UP  ] 4222320 B / 65 拍  → 20.8 Mb/s/连接（最大有效窗口 66832 B）
> [DOWN] 上线 19660800 B / 300 拍 → 21.0 Mb/s/连接
> ```
>
> **三条路的失效模式互不相同，却落在同一点（≈64 KiB/拍）** —— 这比任何单条测量都可信。
>
> ★ 关键的反直觉之处：**窗口缩放开不开，最终数字几乎不变**（20.6 → 20.8）。
> 因为绑定约束不是窗口的**上限**，而是**每个 poll 周期能腾出/补上多少** ——
> 收缓冲要等 `recved()` 才释放、发缓冲要等 ACK 被处理才腾空，而这两件事都只在 poll 里发生。
> 所以哪怕把 `RX_BUF` 和窗口都调大，只要拍子还是 25 ms，稳态仍是一拍一窗。
> 这也说明**单靠调大缓冲救不了**，必须动拍子。

## 一、根因：整条数据面被量化到 40 Hz

### 代码事实（三处，可逐一核对）

1. **喂帧不处理**。`engine::input()`（`engine.rs:322`）只做「学邻居 → 改写端口 → `push_rx`」，
   **不调 `iface.poll()`**。帧就躺在收队列里。
2. **只有一个地方真正推进协议栈**：`poll_collect()`（`engine.rs:493`）—— 收包解析、生成 ACK、
   产生 `ConnData` 事件、`drain_tx` 出帧，全在它里面。
3. **它唯一的调用点是 25 ms 的定时器**：`NetStack.cpp:1006`，泵的 lambda 里。
   `coast_conn_send()` / `coast_conn_recved()`（`engine.rs:761/779`）也都**只动 socket 缓冲、
   不出帧** —— 下行数据写进去、窗口还回去，都要等下一拍才变成线上的包。

于是每个包的实际时序变成：

```
设备发包 ──► Npcap(事件驱动,快) ──► 收队列 ┅┅ 最多等 25 ms ┅┅► poll: 解析+交给 SOCKS
SOCKS 回数据 ──► coast_conn_send(只写缓冲) ┅┅ 最多等 25 ms ┅┅► poll: drain_tx 才出帧
C++ 还窗口 ──► coast_conn_recved(只动缓冲) ┅┅ 最多等 25 ms ┅┅► poll: 窗口更新 ACK 才上线
```

### 实测代价

```
[UP  ] 4222320 B / 65 拍  → 20.8 Mb/s/连接
[DOWN] 上线 19660800 B / 300 拍 → 21.0 Mb/s/连接
```

上行 64958 B/拍、下行 65536 B/拍 —— **两个方向都是一拍搬一个窗口**，
所以这不是"上行有个坑"，是**整条数据面**被同一个拍子卡住。

每拍搬运量 = **通告窗口**，与窗口/RTT 的经典公式一致 —— 只不过这里的「RTT」是
**我们自己的泵周期**，不是链路 RTT。设备与网关同在局域网、真实 RTT 亚毫秒，
却被我们自己的 25 ms 拍子当成了往返时延。

~~**通告窗口只有 65535，没开窗口缩放**~~ —— **这条已证伪**。smoltcp 0.12 支持 WS
（`socket/tcp.rs` 的 `remote_win_scale` / `remote_win_shift`，SYN-ACK 会回选项），
实测设备带 WS 时它回 shift=2。之所以第二版量到 65535，是**我的合成 SYN 没带 WS 选项**。
带上之后有效窗口 262140 B，而吞吐**几乎没变**（20.6 → 20.8）—— 见上面那段反直觉说明。

延迟侧同样：每一个方向的每一跳都 **+12.5 ms 均值 / +25 ms 最坏**。一次 TCP 握手经网关要多
25–50 ms，网页首字节直接慢一档。

### 为什么以前没暴露

- **lwIP 是同步的**：`nif.input(p, &nif)` 当场走完 `ethernet_input → ip4_input → tcp_input →
  回调`，数据立刻交给 SOCKS，`tcp_output` 就地出帧。`pumpToLwip` / `giveBackRecvWindow` /
  `closeConn` 各自直接调 `flushNicTx` —— 那 **6 个 flushTx 收口点**存在的理由正是「出帧发生在
  很多时刻，25 ms 的泵只能当兜底」。
- 代码里甚至写着这句警告：*「别拿它当主路（25 ms 的延迟对 TCP 自时钟是致命的）」*
  —— 而 smoltcp 桥接把**所有**路径都变成了那条兜底路。
- **默认值挡住了它**：`COAST_STACK` 一直默认 `lwip`，smoltcp 只被自测和一次真机试跑碰过。
  自测是 `input(); poll();` 成对调用的，**结构上不可能发现这个问题**。
- ★ 今天移除 lwIP 之后，**这条路成了唯一的默认路径**。

## 二、修它之前必须一起修的一处：`pump_conns` 每拍重拷整个积压

`engine.rs:620-637`：

```rust
let avail = s.recv_queue();
if avail > c.peeked {
    let mut tmp = vec![0u8; avail];          // 按**整个积压**分配
    let got = s.peek_slice(&mut tmp)...;     // 把整个积压拷一遍
    buf.copy_from_slice(&tmp[c.peeked..got]);// 只为取出末尾那几百字节
}
```

因为背压要求「先不 recv」，`c.peeked` 会一直攒着；每有新数据到达，就把**已经交出去过的那部分
再拷一遍**。峰值 128 KiB × 每拍 × 每条连接。

今天 40 Hz，代价是 5 MB/s/连接 —— 难看但不致命。**一旦按下面的方案改成按需 poll（上千次/秒），
它会立刻变成 CPU 瓶颈**：把一个延迟问题换成一个 CPU 问题。所以两件事必须同批做。

（当前 smoltcp 0.12 没有带偏移的 peek。最低成本的缓解是把 `tmp` 挪进 `Conn` 复用，先消掉每拍
的堆分配；彻底消掉那次拷贝需要另设计，不该塞进同一次改动里。）

## 三、修法（建议形状，尚未实施）

保留 25 ms 定时器**只当兜底**（重传/超时仍需要它），另加「有活就 poll」：

```cpp
// 把一次事件循环内产生的所有工作合并成一次 poll —— 不是每帧一次（那是 O(连接数)/帧）。
void smolSchedulePoll(NetStack::Impl *d) {
    if (d->pollScheduled) return;
    d->pollScheduled = true;
    QMetaObject::invokeMethod(d->owner, [d] {
        d->pollScheduled = false;
        coast_stack_poll(d->smol, d->smolClock.elapsed());
        flushNicTx(d);
    }, Qt::QueuedConnection);
}
```

调用点正好对应 lwIP 那 6 个 flushTx 收口点的角色：
- `inputFrame()` 末尾（收帧批 → 合并成一次）
- `smolPumpToStack()` 里 `coast_conn_send` 之后（下行数据到了）
- `smolFlushRecvWindow()` 里 `coast_conn_recved` 之后（窗口还了，ACK 要立刻上线）

⚠️ 收帧是**整批**从 RX 线程投递过来的（`RxWorker` 一次 posted event 一批），所以「每批一次
poll」天然成立，不会退化成每帧一次。

**验证判据**（别只看能不能跑）：三条测量的语义都会变 —— 它们现在都假设「一拍 25 ms」，
改完之后该测的是**单位时间的 poll 次数**与端到端吞吐。
★ 三条都**不要删**：它们的失效模式互不相同，正是靠这一点才收敛出可信的数。
把它们改成"给定 N 次 poll/秒，吞吐是多少"，仍是无真机条件下唯一能证伪的量。

### ⚠️ 这些数全部来自合成对端，**没有一条来自真实 TCP**

三次返工都是同一类错误：**用合成对端模拟真实 TCP 比看上去难**（出窗判定、
SYN 段窗口不缩放、丢包重传……每一条错了都能量出一个看着很像真的假数）。
所以：

- **机制**（整条数据面量化到 40 Hz）—— 确定，三处代码事实可独立核对，不依赖任何测量。
- **数字**（≈21 Mb/s/连接）—— 三个模型收敛，可信，但**仍是合成的**。
- **真机没测**：真实设备 + 真实链路 + 真实 SOCKS/核心叠加之后是多少，没量过；
  N 条连接是否干净地 ×N，也没量过（浏览器多连接场景可能没这么难看，
  但单流下载/测速会直接撞上）。

真要定案，正确做法是让**真实内核 TCP** 当对端 —— `GatewaySelfTest.cpp` 里那套
TAP + 静态邻居 + 真实 curl 的脚手架就是干这个的（现在是 Linux-only，而 NetStack 已收进
Windows；这正是"TPROXY/pf 没有端到端自测"那个已知缺口的另一面）。
真机 A/B 前照例先确认接管生效（靶机 `ip neigh` 的网关 lladdr 已翻成本机 MAC）。

## 四、顺带记下的次要项（都不是当前瓶颈，别顺手优化）

- **上行每字节约 8 次拷贝**：Npcap 内核缓冲 → `RxWorker` 深拷 → `engine::input` 的 `frame.to_vec()`
  → smoltcp 收缓冲 → `tmp` → `buf` → C++ `QByteArray` → `QTcpSocket` 写缓冲。
  其中 `tmp`/`buf` 那两次是上面第二节那个问题，其余属于跨线程/跨语言边界的固有成本。
- **SOCKS 环回**：每个字节多穿两次内核边界（写环回 socket + 核心读）。这是「用户态栈 + SOCKS」
  架构的固有代价，也正是 `npcap-alternatives.md` 里「让 Windows 转发进核心 TUN」那条路
  能一次性省掉的部分。
- **`NetStack.h` 里那组"单线程会不会饿死"的实测**（p50 不劣化、仅尾部毛刺）是 **lwIP 时代**
  测的，同步模型下成立。smoltcp + 40 Hz 量化之后那组数据**不再适用**，需要重测。

## 五、诊断盲区（这次审计暴露的元问题）

`GatewayDiag` 现有的计数器（`pump` / `late` / `maxLagMs` / `usPerTx` / `fpb` / `tcpXmit` …）
**一个都看不见这个瓶颈**：

- `pump`/`late`/`maxLagMs` 量的是「泵有没有按时到」—— 泵**准时**得很，问题是它**太稀**；
- `usPerTx`/`fpb` 量的是 Npcap 侧，而现在根本喂不满它；
- 没有任何一个计数器回答「一个包从进收队列到被处理等了多久」。

这套指标是围绕 lwIP 的**同步**模型设计的，换成 poll 模型之后语义就漏了。
**建议补一条**：poll 周期内处理的帧数 / 距上次 poll 的间隔（即"每拍吃进多少"），
它正是本次量出来的那个量，且能在生产日志里直接看出天花板。

## 附：这次审计推翻了什么、没推翻什么

- **没推翻** R19–R21：那三轮测的是 lwIP + Npcap，当时 lwIP 同步、确实是 Npcap 更紧。
  那个 `PacketSetLoopbackBehavior` 的 2.6× 依然是真实收益。
- **推翻的是它的时效性**：R22 的 smoltcp 移植引入了一个更紧的约束，而移植的验证
  （功能自测 + ABI 自测）**结构上无法发现它** —— 自测总是 `input(); poll();` 成对调用。
- **教训**：换执行模型（同步 → poll）时，功能等价不等于性能等价。旧的性能结论
  **必须连同"它成立的前提"一起复核**，而不是继承。

## 六、逐环节重审（第二遍，2026-08-04）—— 并修正上面那个「Npcap 够不着」

第一遍找到泵量化就收手了，这是**过早收敛**。把每一段都重新过一遍之后，多出三个发现，
其中一个从完全不同的角度独立印证了泵量化；同时**上面那句「Npcap 现在够不着」是错的**。

### 6.1 ★ 先修正：瓶颈是谁，取决于**并发数**

上面的表把 Npcap 一栏写成「否 —— 现在够不着它」。那句话只在低并发下成立。

- 泵量化：≈21 Mb/s/连接 = 2.62 MB/s ≈ **1730 帧/秒/连接**（1514 B 帧）
- Npcap TX：📏 **≈65000 帧/秒**（R20，成本纯每帧、与帧长无关）
- 交叉点：65000 ÷ 1730 ≈ **38 条饱和连接**

| 并发（饱和流） | 绑定约束 | 总吞吐 |
|---|---|---|
| 1 | 泵量化 | ≈21 Mb/s |
| 8（典型浏览器） | 泵量化 | ≈168 Mb/s |
| **≈27–38** | **交叉** | ≈570–790 Mb/s |
| 更多 | **Npcap TX** | 封顶 📏 572 Mb/s |

**两个都是真的，各管一段。** 而用户最容易感知的场景（单文件下载、少流测速、页面首字节）
恰好落在低并发侧 —— 那里是泵量化说了算。所以结论应该是
「**低并发下泵量化，高并发下 Npcap**」，不是「换人了」。

### 6.2 新发现：监听 backlog 是 **32/拍**，突发页面加载会丢 SYN

`LISTEN_BACKLOG = 32`（`engine.rs:44`），而补充监听的 `promote_listeners()` 在
`poll_collect` 里、**排在收包循环之后**：

```rust
loop { iface.poll(...) }      // 这一拍所有 SYN 在这里消耗监听 socket
promote_listeners(nid, out);  // 补充在**之后**才发生
```

所以**一拍之内最多接受 32 条新连接**；同一个 25 ms 窗口里第 33 条起的 SYN 无监听可匹配，
被丢弃或回 RST。设备侧要么等初始 RTO（约 1 s）重传，要么直接报连接失败。

- 建连速率上限 = 32 / 25 ms = **1280 conn/s**（平均值不算低）
- 但**突发**才是问题：一个多源页面同时开 30–100 条连接很常见，超出的部分**每条多付约 1 秒**。

⚠️ 这个和吞吐无关，纯粹是**首屏延迟**杀手，且症状是"偶发某些资源加载特别慢"，
非常难归因。`conns_refused` 计数器已经存在，但它数的是别的路径（见 `engine.rs:584/594`），
**backlog 耗尽这条路没有计数**。

### 6.3 新发现：收帧背压**形同虚设**，真正的积压落在一个无界队列里

`RxWorker` 有一套精心设计的反压（高水位 8192 帧，宁可让收帧线程等、也绝不用户态丢帧，
类注释里写得很清楚）。但它**永远不会触发**：

```cpp
emit frameReceived(f);        // → NetStack::inputFrame → coast_stack_input
...
m_rx->consumed(frames.size()); // 整批立刻记为"已消费"
```

`consumed` 的语义变成了「**已交给引擎**」而不是「已处理」。而引擎那边：

```rust
fn push_rx(&mut self, frame: Vec<u8>) { self.rx.push(frame); }   // 普通 Vec，无界
```

于是：工作线程永远"跟得上"，`outstanding` 立刻回落，8192 的高水位形同虚设；
**真实积压转移到了引擎里那个无界 `Vec<Vec<u8>>`** —— 没有上限、没有计数器、没有反压。

千兆线速 + 25 ms 一拍 ⇒ 每拍约 2000 帧 / 3 MB 常态驻留；工作线程一旦卡顿，它会线性增长。
而且这些帧里**大部分在 poll 时会因出窗被丢掉**（窗口只有一拍的量）—— 白拷、白排、白丢。

★ 这个仓库被同一类问题咬过：`clashauto-gateway-dns-flood-crash` 那次就是无界积压 + 洪水。
被劫持设备是**不可信输入源**，这里应当有界并计数。

### 6.4 ★ 独立印证：一条本该是主路的 `flushTx` 已经变成空操作

`L2Endpoint_win.cpp` 每批收帧的末尾有这么一段，注释写得很明确：

```cpp
// 这一批喂完，lwIP 顺带打出来的 ACK/数据段/ARP 抢答都还在发送队列里 —— 一次收口。
// 「收 N 帧 → 发 M 帧」这条批量链路就是在这里成立的。
flushTx();
```

**这条链路现在不成立了**：喂完一批帧之后，smoltcp 什么都没产出（没 poll），
所以这次 `flushTx()` 刷的是一个空队列。

这一点的价值在于：它是**从完全不同的代码位置、由代码自己的设计意图**给出的印证 ——
不依赖我的任何测量。原设计假定「喂帧 ⇒ 立刻有出帧」，而这个假定随 lwIP 一起消失了，
却没人改这里的注释。**注释与现实的这处背离，本身就是那个 bug 的化石。**

### 6.5 逐环节账本

| # | 环节 | 上限 / 代价 | 依据 | 判定 |
|---|---|---|---|---|
| 1 | 物理链路 | 1 Gbps | — | 否 |
| 2 | NIC → Npcap 内核缓冲 | 4 MiB，满即丢 | 代码 | 有 `rxdrop` 计数，未观测 |
| 3 | Npcap → RxWorker | 每帧一次深拷 | 代码 | 未测，估计不紧 |
| 4 | RxWorker → 工作线程 | **反压失效**（6.3） | 代码 | ★ 设计意图已破 |
| 5 | 引擎收队列 | **无界，无计数**（6.3） | 代码 | ★ 不可信输入源 |
| 6 | **poll 量化** | **≈21 Mb/s/连接；+25 ms/RTT** | 实测 ×3 | ★★ **低并发主瓶颈** |
| 6b | 监听 backlog | **32/拍**，超出丢 SYN（6.2） | 代码 | ★ 首屏延迟 |
| 7 | `pump_conns` 重拷 | 每拍每连接拷一遍积压 | 代码 | 今天不紧，**修 6 之后会紧** |
| 8 | SOCKS 环回 | 每字节多穿 2 次内核边界 | 代码 | 未测 |
| 9 | 核心中继 | 📏 0.38（直连）~0.45（加密）核/Gbps | 旧实测 | 否 |
| 10 | **Npcap TX** | 📏 65k pps / 572 Mb/s | R19–R21 | ★★ **高并发主瓶颈** |

### 6.6 修的顺序（按"改动小 × 收益大 × 风险低"排）

1. **6.2 backlog**：把 `promote_listeners` 挪到收包循环**之前**（或循环内补充）。
   一行位置调整，立刻把"一拍 32 条"变成"一拍不限"。**最便宜的一项。**
2. **6 poll 量化**：合并成"每事件循环一次 poll"（见第三节）。收益最大。
3. **7 `pump_conns` 重拷**：必须与 2 同批，否则延迟问题变 CPU 问题。
4. **6.3 收队列有界化 + 计数**：安全项，与性能无关但同源。
5. 6.4 只是注释，随 2 一起改掉。

★ 全部做完之后**必须重测**：这些改动会把负载重新压到 Npcap 上（第 10 项），
届时 R19–R21 的结论重新成为主约束 —— 那时才轮到 `npcap-alternatives.md` 里
「让 Windows 转发进核心 TUN」那条路。

## 七、修完之后的实测（2026-08-04）

第六节列的修法已落地（commit d3b0589 / 31ae9ad）。逐条对账：

### 7.1 poll 提频 —— **绑定约束按预测回到了 Npcap**

`throughput_scales_with_poll_rate` 把推进周期变成参数扫了一遍：

| 推进周期 | 上行 Mb/s | 下行 Mb/s |
|---|---|---|
| 25 ms（改之前的生产值） | 20.8 | 21.0 |
| 5 ms | 103.9 | 104.9 |
| **1 ms** | **519.7** | **524.3** |

干净的线性关系，与模型逐字吻合：**每连接吞吐 ≈ 有效窗口 ÷ 推进周期**。

生产现在是「每轮事件循环 poll 一次」，负载下是亚毫秒级 ——
所以单连接天花板从 21 Mb/s 抬到了 **≈520 Mb/s 以上，即 Npcap 的 572 Mb/s 附近**。
★ 这正是第六节结尾预告的结果：**修完之后瓶颈重新变成 Npcap**，
于是 `npcap-alternatives.md` 里那条「让 Windows 转发进核心 TUN」的路重新成为主线。

时延侧有真机量级的证据（自测里的可证伪断言）：

```
摘掉 schedulePoll → FAIL: SYN-ACK 用了 23875 us
接上             → PASS: 375 us
```

**每个 RTT 少 ~24 ms。** TLS 握手要过好几个来回，首字节的改善是这个数的倍数。

### 7.2 backlog —— 一拍 32 条的封顶已拆

`backlog_does_not_cap_accepts_per_poll`：一拍喂 100 个 SYN，100 个全回 SYN-ACK。
已验证可证伪（把 `PROMOTE_EVERY` 调大 → 只回 32）。

★ 修的过程本身值得记：**第一版修法无效，是新加的测试抓住的。**
我以为把 `promote_listeners` 挪进收包循环就行，但 smoltcp 的 `Interface::poll()`
**内部会一直 receive() 到设备说没有为止** —— engine 里那句「一次 poll 只处理一帧」的
老注释是错的。一次调用就吃光全部 32 个监听，补充逻辑根本没机会插进去。
真修法是给 `QueueDevice` 加取帧预算，把一次 poll 切成小块。

### 7.3 还没做的

- **收队列有界化 + 计数**（6.3）。安全项，与性能无关但同源：被劫持设备是不可信输入源。
- **真机 A/B**。以上全部来自合成对端；真实设备 + 真实链路 + 叠上 SOCKS 与核心之后是多少，
  仍然没量。按 7.1 的预测，那时该看到瓶颈落在 Npcap 的 65k pps 上 —— 但**预测不是测量**。

## 八、★ 推翻 R19–R21 的前提：那 12–17 µs/帧**不是 Npcap，是 QEMU 的 e1000 模拟**

2026-08-04。修完前面几项之后，绑定约束按预告回到了 Npcap，正准备照
`npcap-alternatives.md` 动手换发送路径 —— 动手前先回答一个一直标着「未定」的问题：

> **65k pps / 12–17 µs 每帧，到底是 Npcap 的成本，还是这台 QEMU 上 e1000 模拟的成本？**

这台机器上正好有两张网卡，构成了干净的判别器：

- `以太网 2` —— Intel PRO/1000 MT，**QEMU 模拟的硬件**，1 Gbps
- `vEthernet (Default Switch)` —— Hyper-V 虚拟网卡，**不是模拟硬件**，10 Gbps

同一个 Npcap、同一个 `npcap_tx3.exe`、同样的 batch/loopback/抓包句柄设置，只换网卡：

| 网卡 | CPU µs/帧 | 核/Gbps | 吞吐 |
|---|---|---|---|
| Hyper-V 虚拟（非模拟硬件） | **2.9 – 3.8** | **0.25 – 0.31** | 628–679 Mb/s |
| QEMU 模拟 e1000 | **16.4 – 17.9** | **1.39 – 1.52** | 482 Mb/s |

**每帧 CPU 差 5.5 倍。** 而且在 Hyper-V 那张卡上：

- 批量 64 / 256 / 512 **结果一致**（2.9~3.7 µs）→ 攒批早就饱和了，不是这里的问题
- 抓包句柄开不开**也一致** → R20 那个 `NPF_DoTap` 2.6× 的效应同样是 e1000 特有的
- **只用了 ~18% 的一个核**（0.9s CPU / 5.3s 墙钟）却卡在 ~650 Mb/s
  → 那 650 不是 CPU 上限，是 Default Switch 自己的速率，**Npcap 侧还有大量余量**

### 8.1 先验证帧真的上线了（这条不做，上面全是废的）

按本仓库反复栽过的那条纪律：**用组件自己的计数器对一次量级**。

| 网卡 | 独立计数器 | 结果 |
|---|---|---|
| Hyper-V | `Get-NetAdapterStatistics.SentUnicastPackets` | 提交 200000 → 计数 **200000（100%）** |
| e1000 | perfmon `\Network Interface(...)\Packets Sent/sec` | 全程 **43.4k–44.9k pps**，与提交速率 43.1k 吻合 |

（e1000 那张卡不出现在 `Get-NetAdapterStatistics` 里，第一次查到 0 是**查不到**、不是没发出去 ——
差点又照着假数据下结论。）

两边都真的上线了。所以 5.5 倍是**纯 CPU 成本差**，且差在 Npcap **之下**的网卡层：
每帧一次 TDT 写 = 一次 VM exit，e1000 模拟在 QEMU 里不做 TX 合并、也没有 ioeventfd。

### 8.2 这推翻了什么

**R19–R21 的核心结论「Windows 网关的绑定约束是 Npcap 发送路径」，在非模拟网卡上不成立。**

真实的 Npcap 发送成本约 **0.25 核/Gbps** —— 与 Linux TPROXY 的 📏 0.25 核/Gbps **同一量级**。
也就是说：在真实硬件上，Npcap 这条路本来就不慢，它只是**在这台 QEMU 上慢**。

连带作废的：

- ❌ 「📏 硬顶 ≈65k pps」—— 那是 e1000 模拟的顶，不是 Npcap 的顶
- ❌ 「换栈的收益是省 CPU 约 1/3」—— 分母（Npcap 那份）被高估了 5.5 倍
- ❌ `npcap-alternatives.md` 里以 12 µs/帧 为前提的全部折算
- ⚠️ R20 的 `NPF_DoTap`/抓包句柄 2.6× 效应 —— 在 Hyper-V 卡上量不到，同样疑似 e1000 特有
  （`PacketSetLoopbackBehavior` 那一行**仍然该留**：它零成本、且在真机上无副作用，
   只是别再拿"2.6×"当它的收益）

**没有**被推翻的：
- ✅ smoltcp 换掉 lwIP —— 那是两个用户态栈的对比，与网卡无关
- ✅ poll 提频（21 → 520 Mb/s/连接）—— 纯软件量化问题
- ✅ backlog / 无界队列 / O(n²) 那几项 —— 都是代码结构问题

### 8.3 现在该做什么

**先别动 Npcap。** 换发送路径（WFP / TUN 重定向）是个大工程，而它的全部理由建立在一个
已被证伪的前提上。正确的下一步是**在一台真实 Windows 机器上量一遍**：

1. 真机 + 真实网卡上跑 `npcap_tx3.exe`，看 µs/帧 落在 3 还是 17
2. 若接近 3 → Npcap 不是瓶颈，`npcap-alternatives.md` 整条线降级为「以后再说」
3. 若仍接近 17 → 那才轮到换路径，且届时的判据是**真机数字**

⚠️ 本节所有数字仍来自**这台 QEMU 虚机**。它证明的是「同一驱动在两种网卡上差 5.5 倍」
这个**相对**事实（这一条足以推翻绝对值），但 3 µs/帧 本身也是虚拟环境里的数，
**不能直接当作真机预期**。

## 九、把网卡拿掉之后：**大头是我们自己的代码，而且是「每字节」的**

第八节证明了台子的网卡模拟污染了此前所有数字。那么去掉网卡，我们自己这段代码值多少 CPU？
新增 `COAST_GW_THROUGHPUT=1`（`runGatewayThroughputBench`）：`FakeEp` 不碰任何驱动，
出帧直接落进内存，量的是

```
inputFrame → coast_stack_input → schedulePoll → poll → conn_data
→ Socks5Tcp::write → 回环 socket → 假 SOCKS
```

**这个数与网卡无关，因而可跨机器比较**，也是 poll 提频那次改动在集成层面的回归护栏
（Rust 侧的 `throughput_scales_with_poll_rate` 只覆盖引擎，不含 C++ 桥接与 SOCKS）。

### 9.1 基线（三次重复，离散 <3%）

```
送达 33616800 B / 0.64s → 422~424 Mb/s；CPU 0.62~0.64s
扣掉夹具造帧 1.56 us/帧 → 净 24.47~25.12 us/帧, 2.18~2.24 核/Gbps
```

CPU 占了 **97% 的一个核** ⇒ **422 Mb/s 就是这台机器上单线程软件路径的天花板，与网卡无关。**

对比第八节量到的 Npcap（非模拟网卡）**≈3 µs/帧、0.25 核/Gbps**：

| | µs/帧 | 核/Gbps |
|---|---|---|
| Npcap 发送（真实网卡量级） | ~3 | 0.25 |
| **我们自己的软件路径** | **~24.5** | **2.2** |

⇒ **网关的主要成本是我们自己的代码，不是 Npcap（约 8:1）。**

### 9.2 判别器：每帧固定成本 vs 每字节成本

这两者的修法完全不同，不先分清就是瞎优化。用 `COAST_GW_BENCH_PAYLOAD` 扫载荷：

| 载荷 | 净 µs/帧 | 吞吐 Mb/s |
|---|---|---|
| 1400 | 22.64 | 423 |
| 700 | 14.85 | 423 |
| 350 | 6.05 | 403 |
| 128 | 1.72 | 364 |

**判据是「吞吐几乎不变」**（423 / 423 / 403 / 364）：
若成本是每帧固定的，小载荷会让吞吐塌下去；实际它基本不动 ⇒ **成本几乎全是每字节的**。

线性拟合 `cost = a + b·bytes`：
- b ≈ **0.0164 µs/字节 = 16.4 ns/字节**
- a ≈ **-0.4 µs ≈ 0**（在噪声内）——**每帧固定开销可忽略**

⇒ **攒批、减事件派发、降 poll 次数这类"省每帧开销"的优化，在这条路径上拿不到东西。**
   要提速只能**砍每字节的活**。

### 9.3 17 ns/字节意味着什么

单次 `memcpy` 大约 0.1~0.2 ns/字节。**17 ns/字节 ≈ 一次 memcpy 的百倍**，
所以这里不是"多拷了一两次"，是一条很长的每字节流水线。清点上行方向（本基准覆盖的部分）：

| # | 每字节的活 | 位置 |
|---|---|---|
| 1 | `frame.to_vec()` | `engine.rs::input`（拥有帧才能入队） |
| 2 | TCP 校验和**验证** | smoltcp 收包 |
| 3 | 拷进 socket 的接收环 | smoltcp |
| 4 | `peek → to_vec()` | `pump_conns`，造 `Event::ConnData` |
| 5 | `QByteArray(data, len)` | `smolConnData` |
| 6 | 拷进 QTcpSocket 写缓冲 | `Socks5Tcp::write` |
| 7 | 内核回环发送 | socket |
| 8 | 假 SOCKS `readAll()` | 夹具（生产里是 mihomo 读） |

★ 其中 **4 和 5 是可以一起消掉的**：C ABI 早就写明「回调里的指针只在回调返回前有效」，
而 `Socks5Tcp::write(const char*, qsizetype)` 本来就有零拷贝契约（lwIP 时代的单段 pbuf 快路径
用的就是它）。只要 `conn_data` 能把**指向 smoltcp 接收环的指针**直接交出来，
4、5 两次拷贝加两次分配一起没了。
障碍是 `Event::ConnData` 目前**拥有** `Vec<u8>`（先收集事件、再派发，为的是不持有引擎借用）。
要改成借用，得让 `pump_conns` 在持有 socket 借用的同时就地回调 —— 是个真改动，不是顺手。

⚠️ 还没做归因实验：上面 8 项里到底哪几项占大头，**没有量过**。
   17 ns/字节这个总数是实测，拆解是清单不是测量。下一步应当逐项去掉/短路来定位，
   而不是照着直觉先去改第 4、5 项。

### 9.4 修正路线图

1. ~~换 Npcap 发送路径~~ —— 第八节已证伪其前提，且本节显示它只占约 1/8。**降级。**
2. **归因实验**：把上面 8 项逐个短路，量出各自占比。这是下一步唯一该做的事。
3. 再按归因结果动手（大概率落在拷贝与校验和上，但**别跳过第 2 步**）。
4. 真机验证仍然欠着 —— 本节全部数字来自这台 QEMU 虚机；虽然去掉了网卡这个最大污染源，
   但 CPU 与内存本身仍是虚拟的。

## 十、归因实验：**69% 花在到 mihomo 的那一跳回环上**

第九节量出上行是 ~17 ns/字节、几乎全是每字节成本，但那 8 项各占多少没量过。
这一节用分级短路（`COAST_GW_BENCH_STAGE`）逐段砍掉再量，相邻两级之差就是该段成本。

```
STAGE=0  全路径
STAGE=1  构造 QByteArray 但**不写 socket**   ← 只砍掉「跨进程边界」
STAGE=2  连 QByteArray 都不构造
STAGE=3  再不 poll
STAGE=4  再不调 coast_stack_input
```

★ 1 与 2 **必须分开**。第一版把它们并成一级，于是"回环那一跳"里混进了一次
`QByteArray` 分配+拷贝 —— 那会让跨进程边界的占比被高估。分开之后才量得清。

★ 短路必须在**握手完成之后**才打开 —— STAGE≥2 关掉 poll，而三次握手本身要 poll，
开在前面连连接都建不起来（第一版就是这么废掉的，见 `coastSetBenchStage` 的注释）。

### 10.1 结果

| STAGE | 净 µs/帧 | 段差 = 该段成本 | 占比 |
|---|---|---|---|
| 0 全路径 | 22.02 | — | 100% |
| 1 构造 QByteArray 但不写 socket | 7.63 | **14.39** | **65%** ← **写缓冲 + 内核回环 + 对端读** |
| 2 连 QByteArray 都不构造 | 7.63 | **0.00** | **≈0%** ← 那次分配+拷贝 |
| 3 不 poll | 0.26 | **7.37** | **33%** ← 校验和验证 + 收环拷贝 + peek/to_vec + 事件派发 |
| 4 不喂帧 | 0.09 | 0.17 | 0.8% ← `frame.to_vec` + portmap 改写 |
| （夹具底噪） | — | 0.09 | 0.4% |

加和自洽：14.39 + 0.00 + 7.37 + 0.17 + 0.09 = 22.02 ✓

**两个附带结论：**

1. **`QByteArray` 那次分配+拷贝量不出来**（STAGE 1 与 2 完全相同，在 ~4% 的分辨率内）。
   1400 字节的堆分配+memcpy 在这条路径上是噪声级 —— **"少拷一次 QByteArray"不值得做**。
2. **各级的背压次数都是 0**（上行节流 0~1 次、下行暂停 0 次，基准会打印）。
   这条必须核对：STAGE=1 之后 `bytesToWrite()` 恒为 0，若 STAGE=0 曾大量节流，
   两者的**流态**就不同、相减无意义。实测没有，**归因成立**。

### 10.2 ★ 结论与直觉相反，先做归因是对的

第九节我列清单时最想改的是 `peek → to_vec → QByteArray` 那两次拷贝（清单第 4、5 项）。
归因显示：其中 `QByteArray` 那次**成本量不出来**，另一次落在协议栈那 33% 里只是一部分；
而**喂帧路径（`frame.to_vec` + portmap）只占 0.8%** —— 花力气优化它几乎等于白干。

这正是第九节结尾写的那句「别照直觉先去改第 4、5 项」的价值。**再次验证：先量再改。**

### 10.3 那 69% 是什么，怎么去掉

是**把字节从我们的进程搬到 mihomo** 这一跳：
QTcpSocket 写缓冲 → 内核回环 TCP → 对端读。
（`QByteArray` 的构造已经被 STAGE=1/2 单独剥离出去了，**不在这 65% 里**。）

- 折算 **10.3 ns/字节**。单次 memcpy 约 0.1~0.2 ns/字节，所以这不是"拷贝贵"，
  是整套回环 TCP 机制（AFD、回环分段、Qt 的可读通知、两侧缓冲管理）贵。
- ⚠️ 而且这是**下界**：夹具那侧用的是 `QIODevice::skip()`（不构造 QByteArray），
  比真实 mihomo 读+解析便宜。真实场景只会更贵。
- 载荷扫描（第九节）已证明它是**每字节**而非每系统调用的成本，
  ⇒ **合并写、攒批发这类"减少 write 次数"的优化拿不到东西。**

**唯一能真正拿掉这 69% 的做法是不走这一跳** —— 即**进程内出站**：
网关直接把连接交给进程内的出站实现，而不是经回环 SOCKS 交给外部核心。
本仓库已有这条线（见记忆 `clashauto-coastcore`：进程内出站，TCP 协议零新依赖）。

⇒ **Windows 网关性能的下一个大头不在数据面，在「我们和核心之间那道进程边界」。**

### 10.4 修正后的优先级

| 项 | 收益 | 状态 |
|---|---|---|
| **进程内出站（去掉回环 SOCKS 跳）** | **~65% 软件 CPU** | ★ 最高，且已有在建的线 |
| 协议栈那 33%（校验和/收环/peek） | 至多 33%，且要动 `Event::ConnData` 的所有权 | 次之 |

### 10.5 仍然欠着的

- 全部数字来自这台 QEMU 虚机。第八节已经把最大的污染源（网卡模拟）排除在外，
  但 CPU 与内存本身仍是虚拟的 —— **相对占比可信，绝对值别当真机预期。**

## 十一、那 65% 不用从头做：`feat/coastcore-outbound` 上已经有了

查证（2026-08-04）：进程内出站不是待开工的想法，而是一条**已经落地 109 个提交**的分支。
`feat/coastcore-outbound` 上：

- `src/net/IOutbound.h` —— 出站抽象（`IOutboundTcp` / `IOutboundUdp`）
- `src/net/core/` —— `CoreRouter` / `CoreDialerFactory` / `DirectOutbound` /
  `RuleEngine` / `DnsResolver` / `ProxyConfig*` / `proto/Hysteria2Outbound` …
- ★ **`NetStack` 在那条分支上已经改用 `IOutboundTcp`**，不再直接 `new Socks5Tcp` ——
  也就是说「网关不经回环 SOCKS」这件事在**架构上已经解决**，只是没并回来。

### 11.1 两次独立测量互相印证，而且是**互补**的

| | `feat/coastcore-outbound`（899c845） | 本分支（第九、十节） |
|---|---|---|
| 指标 | 轻载**延迟** | **CPU 占比** |
| 结果 | 22.3 ms → **14.3 ms（快 36%）** | 回环那一跳占软件成本 **65%** |
| 手段 | 去掉 mihomo 回环 | （量化，未改） |

两者量的是同一件事的两个侧面，方向一致 —— **相互独立地支持"去掉回环那一跳"**。

★ 更值得注意的是那条分支当时把**剩余**时间定位在哪：
> 剩下的两段都在 lwIP 这一侧：设备 SYN → SYN-ACK 约 4.4 ms（本该是微秒级），
> 以及请求转发/应答回送约 10 ms。对照内核转发全程只要 0.5 ms。

那正是本分支这几轮在修的那**一类**问题（数据面把帧攒到下一拍才发/才处理）。
⚠️ 但**不能说"我修好了他们那 4.4 ms"**：那个数是 lwIP 上的，而 lwIP 已被移除；
smoltcp 上的同类问题更严重（SYN-ACK 23.9 ms），现在是 0.375 ms。

### 11.2 合并的代价要说清楚

两条线**都需要**，但合并不是顺手的事：**双方都重写了 `NetStack.cpp`**。
- 那条分支：把 `Socks5Tcp` 换成 `IOutboundTcp`（改的是**出站**那一侧）
- 本分支：删掉 lwIP、接 smoltcp、poll 提频、背压重写（改的是**数据面**那一侧）

好消息是两处改动**在文件里基本不重叠**：出站是 `SmolConn::socks` 那 5 个信号连接，
数据面是帧路径与 poll。所以把 `IOutbound.h` 的接口拿过来、把本分支的
`Socks5Tcp *socks` 换成 `IOutboundTcp *socks`，是**几行的机械改动**；
真正的工作量在那 109 个提交里的其余部分（路由、规则、DNS、各协议出站）。

### 11.3 建议

这是**要不要并一条 109 提交分支**的决定，属于产品/发布节奏的事，不是我该替你定的。
两件事已经清楚：
1. 那 65% 有现成实现，不必重做；
2. 两条线互补、都不可省 —— 只并出站不修量化，单连接仍卡在 21 Mb/s；
   只修量化不并出站，65% 的 CPU 还在原地。

## 十二、拆那 33%：校验和不是主因；以及一个**差点发布出去的假结论**

第十一节把 65% 那一项交给了 `feat/coastcore-outbound`。这一节拆第二优先级——
协议栈那 33%（7.37 µs/帧）里，校验和验证与拷贝各占多少。

### 12.1 ★ 先说那个假结论：开关根本没生效

做法是给 smoltcp 的 `DeviceCapabilities` 设 `checksum.tcp = Checksum::Tx`
（发送仍生成、收包不验），比对开关前后的成本。第一版实现是「建完网卡之后再改设备」，
量出来 **7.63 vs 7.70 µs/帧**，看着就是"校验和不要钱"。

**这个结论是假的。** 写证伪测试时才发现：

```
skip_rx_checksum_knob_actually_works
  · 喂一个校验和故意写错的 SYN，默认应被丢弃            → ✅ 通过
  · 关掉验证后同一个坏帧应被接受                        → ❌ 仍被丢弃
```

根因：**smoltcp 的 `Interface::new()` 会把 device 的 capabilities 拷进
`InterfaceInner` 缓存起来**，建好之后再改设备是没有效果的。
开关必须在 `add_nic`（以及 C++ 侧的 `NetStack::addNic`）**之前**设。

⇒ 教训与本仓库既有的那条同源：**「开关看着开了」≠「开关生效了」。**
   对照实验必须先证明"被关掉的东西真的被关掉了"，否则两边量的是同一个东西，
   得到的"没差别"完全没有信息量。这条已经补成常驻测试。

### 12.2 修好之后的结果：校验和低于噪声

| 配置 | 五次（µs/帧） | 中位 |
|---|---|---|
| 验校验和 | 7.63, 7.63, 6.56, 6.40, 7.70 | **7.63** |
| 不验校验和 | 6.40, 7.63, 5.18, 7.63, 9.08 | **7.63** |

中位数完全相同，离散约 ±25%。⇒ **校验和验证的成本低于本基准的噪声底**，
不是那 33% 的主要成分。（也就是说：即便愿意牺牲正确性去关它，也换不到东西。）

⚠️ 顺带明确：**关收包校验和在生产上本来就不可接受**。我们是中间盒，终结设备的 TCP 之后
再以新连接转发，转发时会算一个**有效**的校验和 —— 收包不验 = 把损坏数据洗成
"看起来正确"的新连接，端到端校验就此失效。以太网 FCS 逐跳重算，救不了这个。
所以这个开关只是测量工具（`coast_stack_debug_skip_rx_checksum`），不是可选项。

### 12.3 那 33% 是什么

排除校验和之后，剩下的是 **smoltcp 的每包常规开销**：收环拷贝、`peek → to_vec`、
事件派发、头部解析与 seq/ack 记账、socket 状态机。**没有单独一块可以摘掉**——
它是弥散的，不存在"改一处省一半"的机会。

⇒ 这反过来加强了第十一节的结论：**值得投入的是那 65%（去掉回环那一跳），不是这 33%。**

### 12.4 本节新增的常驻测试

- `skip_rx_checksum_knob_actually_works` —— 钉住"关校验和"这个测量工具本身是有效的。
  没有它，12.1 那个假结论会被当成事实写进文档。
