# Npcap 的替代方案分析（Windows 透明网关）

> 2026-08-04。承接 `lwip-alternatives.md` 的 R19–R21：那三轮把「Windows 网关的绑定约束是
> **Npcap 发送路径**，不是 TCP 栈」量清楚了，并靠一行 `PacketSetLoopbackBehavior` 拿到 2.6×。
> 本文回答下一个问题：**这条发送路径本身能不能换掉。**
>
> 本文是**分析**，不是实测轮次。凡是标 📏 的数字来自本仓库已有实测；标 🔍 的是查证的外部事实；
> 标 💭 的是推理，**尚未验证**。别把 💭 当结论用。

---

## 0. 先把问题问对：Npcap 在这里其实干**两件**事

拆开之后整个问题的形状就变了 —— 这是本文最重要的一句话。

| 角色 | 谁在用 | 帧率量级 | 对 Npcap 的敏感度 |
|---|---|---|---|
| **A. ARP/NDP 投毒** | `ArpSpoofer` / `NdpSpoofer` | **几帧/秒**（周期重播 + 撤销时还原） | 几乎为零。12 µs/帧 × 5 帧/秒 = 0.006% CPU |
| **B. 数据面收发** | `NetStack` ⇄ `L2Endpoint_win` | **上万帧/秒**，📏 硬顶 ≈65k pps | 全部成本在这里 |

📏 R20 已证明成本是**纯每帧**的（78 B 与 1514 B 的 µs/帧完全一致），所以角色 A 的开销
在任何量级上都可以忽略，而角色 B 撞的是 pps 天花板。

**推论：不必"替换 Npcap"，只需要把角色 B 挪走。** 下面所有方案都按这个口径评价。
一个只能替代 A 的方案毫无价值（A 本来就不疼），一个能挪走 B 的方案即使仍需 Npcap 做 A，
也已经解决了全部问题。

## 1. 还有一个与性能无关、但更该先看的理由：许可与安装摩擦

即使性能完全够用，Npcap 仍有两个**产品级**问题：

- 🔍 **Npcap 免费版许可不允许随产品分发，也不允许静默安装**（只有付费 OEM 版可以）。
  这一点代码里早就记着：`src/qml/NpcapInstaller.cpp:471` —— 「Npcap 免费版的许可只允许
  OEM 版静默安装」。当前做法是运行时从 npcap.com 下载让用户自己点，规避了分发问题，
  但换来了安装摩擦。
- **默认安装选项会让网关直接不可用**：安装向导的
  「Restrict Npcap driver's access to Administrators only」**默认勾选**，勾上后非提权的
  Coast 必然 `pcap_open_live` 失败（拒绝访问 5）。`NpcapStatus.h` 整个文件的存在就是为了
  把这个坑和「没装」区分开，`NpcapInstaller::fixPermissions` 是专门为它写的一键修复。

也就是说：**每个 Windows 用户想用网关，都要装一个第三方驱动、还大概率要再修一次权限。**
任何能去掉这一步的方案，即便性能持平也是净赚。

## 2. 候选清单

### 2.1 直接被排除的（写出来是为了不再重复调研）

| 候选 | 为什么不行 |
|---|---|
| **WinPcap** | 🔍 2013 年即停更，不支持 Win10+。Npcap 就是它的继任者 |
| **Win10Pcap** | 🔍 2015 年后无维护 |
| **原始套接字 `SOCK_RAW`** | 🔍 Windows 自 XP SP2 起禁止用原始套接字发 TCP、且禁止伪造源地址；且它是 L3，**根本没有 L2 注入能力** |
| **PktMon**（Win10 1809+ 内置） | 🔍 只抓不发，ETW 输出，是诊断工具。它的存在恰好证明 **Windows 没有内置的帧注入通道** |
| **WinDivert** | 🔍 工作在 WFP 的网络层，**不是 L2**；且 `WfpRedirect.h:71-76` 已记录：Windows 在该层之下强制 TCP 反欺骗，用户态无法注入"源地址是外部 IP"的包。**架构性做不到**，别再试 |
| **DPDK / PacketDirect** | 需要特定网卡 + 独占该网卡（用户的上网网卡不能被独占）。消费级场景不成立 |
| **Hyper-V vSwitch 扩展** | 只在开了 Hyper-V 的机器上有 vSwitch，且同样要 EV 签名 |

### 2.2 值得认真评估的三条

#### ① XDP-for-Windows

🔍 微软开源（MIT）的 AF_XDP 实现，提供**真正的 L2 收发**，NBL 池化 + 串链 + 单次调用，
发布版驱动由微软签名。

- **优点**：正面解决角色 B —— 它的批量提交模型正是 `PacketSendPackets` 每帧一次 NDIS 送出的对症解法。
- **致命问题**：🔍 **不支持 Wi-Fi**（`lwip-alternatives.md` R21 末尾已记录这一点）。
  而家用场景里被代理的手机/平板几乎全在 Wi-Fi 上，网关本机也常是 Wi-Fi。
- 其他阻力：仍需装驱动（换了一个第三方依赖，没消掉安装摩擦）、无成熟安装器、用户基数近零。
- ⚠️ R21 那条记录是**当时的调研结论，值得复核**（该项目在演进）。但即使 Wi-Fi 支持了，
  "换一个装机量更小的驱动"在产品上也很难说是进步。

**结论：技术方向对，产品上不划算。** 除非将来 Coast 明确只面向有线场景。

#### ② 自写 NDIS 轻量级过滤驱动（LWF）

就是"自己做一个 Npcap"。能拿到最优性能（免掉 BPF 遍历、免掉 loopback 扫描、按需批量），
且可以只暴露我们要的两个操作。

- **阻塞与 `WfpRedirect.h` 完全同源**：EV 代码签名证书 + 微软硬件门户 attestation 签名。
  这不是写代码能解决的，先得有证书。
- 开发量远大于 WFP callout（要处理 NDIS 各种收发路径、暂停/重启、绑定变化）。

**结论：性能上限最高，但被签名条件卡死，且投入产出比最差。** 有了 EV 证书之后，
同样的签名成本更该花在 ③ 的替代方案 `WfpRedirect` 上（那条能直接干掉整个用户态数据面）。

#### ③ ★ 让 Windows 自己转发，把数据面交给核心的 TUN —— **不需要任何新驱动**

这是本文唯一一条**既能挪走角色 B、又不引入新的签名/安装依赖**的路径。

**思路**：ARP/NDP 投毒照旧（角色 A 仍用 Npcap，成本可忽略），但**不再把设备的帧喂进
用户态栈**。改为打开 Windows 的 IP 转发，让设备的包被 Windows 路由；而核心的 TUN 模式
本来就会装一条低跃点的默认路由 → 这些包自然走进 TUN → 核心的 TUN 入站按原始目的地代理。

**为什么值得认真对待：这个对比的两个数本仓库都已经量过。**

| 数据面 | 吞吐 | CPU | 出处 |
|---|---|---|---|
| Npcap TX（修掉 loopback 后，**只算发送**） | 📏 **572 Mbps** | 📏 **1.26 核/Gbps** | `lwip-alternatives.md` R21 |
| 核心自带 TUN（Windows，system / gvisor 两栈实测等价） | 📏 **2743 Mbps** | 📏 **0.45 核/Gbps** | `NetStack.h`「核心自带 TUN 的两个栈」一节 |

📏 **≈4.8× 吞吐、≈1/3 CPU** —— 而且 Npcap 那一栏还**没算**收方向、没算 TCP 栈、没算 SOCKS 桥接。
两个数据面之间不是"优化几个百分点"的关系，是一个数量级的结构差异。

⚠️ **这个对比有一条必须说明的口径差**：TUN 那组量的是**本机自己的流量**走 TUN，
不是"从局域网转发进来的流量"走 TUN。转发多一跳，成本会上去一些。💭 但数据面的成本结构
（每包一次内核态搬运，没有 65k pps 的用户态往返天花板）是同一个，**量级结论应当成立**。
两组数字是否来自同一台机器也要核对后再引用。

**这条路顺带解决/简化的东西**（不是附赠，是它比换驱动更有价值的原因）：

- **`NetStack` 在 Windows 上也不再需要** —— 用户态 TCP 栈、UDP NAT、DNS 劫持那 1600 行
  全部退场，`rust/coaststack` 同样退场。三端就都只剩内核数据面了（Linux TPROXY /
  macOS pf / Windows 转发+TUN），架构第一次真正对齐。
  ★ 说清楚：这意味着**刚做完的 smoltcp 移植在 Windows 上也会变成死代码**。
  沉没成本不该影响判断 —— 但也别急着删，见下面「怎么验」。
- **每设备身份归属已经现成**：今天靠 SOCKS 用户名（`inboundUser`）归属，因为经 SOCKS 之后
  `sourceIP` 恒为 127.0.0.1。走 TUN 之后 `sourceIP` **就是设备真实 IP**，而
  `DevicesController.cpp:783-784` 的归属判据本来就是 `sourceIP == ip || inboundUser == user`
  —— **两条路都已经写好了**，设备页不用改。
- **每设备策略**：今天靠 `IN-USER,<user>,REJECT`；走 TUN 改用 `SRC-IP-CIDR`。
  核心侧 `SrcIPCIDR` 规则类型已存在（`constant/rule.go:18`）。
  ⚠️ 同时注意这**修掉**一个已知缺陷：`NetStack.cpp` 里记着「禁网设备的 UDP/DNS 到了核心
  分不出是谁」，所以只能在网关层拦。`SRC-IP-CIDR` 对 UDP/DNS 一视同仁，这个洞自然消失。

**必须先验证的未知**（都是 💭，任何一条不成立方案就废）：

1. **Windows 会不会转发**：需要 `netsh interface ipv4 set interface <if> forwarding=enabled`
   （或 `IPEnableRouter` + 重启）。💭 **Wi-Fi 客户端适配器上的转发是否工作，是最大的问号** ——
   这与 XDP 的 Wi-Fi 问题是同一个致命点，必须优先测。
2. **转发的包会不会进 TUN**：取决于核心装的默认路由跃点与转发路径的路由查找。💭 理论上会。
3. **核心的 TUN 入站能不能正确处理转发流量**：源 IP 不是本机地址，需要确认 TUN 栈
   （system / gvisor）不会因此丢包。
4. **反向路径**：核心回给设备的包，Windows 要能路由回 LAN 接口并 ARP 到设备。💭 应当自然成立。
5. TUN 需要管理员权限 —— 但网关本来就要（Npcap 也要），不是新增约束。

**怎么验（半天，不写新代码）**：用现成的 `COAST_GATEWAY_TESTDEV` 接管一台靶机，
但把喂帧那一步关掉（`m_net` 为空的路径已经存在 —— tproxy/pf 模式就是这么跑的），
打开 Windows 转发 + 核心 TUN，看靶机能不能上网、出口 IP 是不是节点 IP。
★ 开量前必须先确认接管真的生效（靶机 `ip neigh` 的网关 lladdr 已翻成本机 MAC）——
`NetStack.h` 与 `L2Endpoint_win.cpp` 各记过一次栽在这上面的教训。

## 3. 结论与建议顺序

1. **先验 ③ 的第 1 条未知（Wi-Fi 上的 IP 转发）。** 半天、零代码、一票否决。
   它成立的话，Windows 数据面的天花板从 572 Mbps 抬到 2.7 Gbps 量级，
   而且不需要任何新驱动、不需要 EV 证书 —— 这是所有候选里唯一"没有硬阻塞"的一条。
2. **不成立就回到现状**：Npcap + smoltcp 已经处在这条路的最优点
   （📏 R20/R21：批量、线程、帧长、内核路径四个旋钮全试过，loopback 那一项已修）。
   此时唯一剩下的性能杠杆是 **③ 之外的角色 B 替代品**，而它们要么没 Wi-Fi（XDP），
   要么要 EV 证书（自写 LWF）。
3. **无论 ① ② ③ 哪条，Npcap 都不会完全消失** —— 角色 A（ARP/NDP 投毒）仍然需要它，
   因为 Windows 没有任何内置的 L2 注入通道。所以"去掉 Npcap 依赖 / 去掉安装摩擦"
   **不是一个可达目标**，除非将来走 `WfpRedirect.h` 那条内核重定向路线（连投毒都不需要）。
   这一点要对产品侧说清楚，别承诺"以后就不用装 Npcap 了"。
4. **暂不删除 smoltcp/NetStack。** 它是 ③ 失败时的唯一数据面，而 ③ 有一条一票否决的未知。
   等 ③ 真机跑通再谈。

### 一条方法论（承接 R21 的教训）

R20 说过一次「Npcap 内部优化空间已穷尽」，R21 就用一行开关打脸 2.6×。这次的对称风险是：
**"Npcap 已到最优点"这个结论只在"角色 A 和角色 B 都必须用它"的前提下成立。**
一旦把两个角色拆开，问题就从"怎么让注入更快"变成"数据面能不能根本不走注入" ——
后者已经有 4.8× 的现成实测在手。**重问一次题目，往往比再拧一次旋钮值钱。**
